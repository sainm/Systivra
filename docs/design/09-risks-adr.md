# 第九部分：风险与决策

## 1. 风险登记册

评级：可能性 / 影响 均为 高·中·低。RPN ≈ 影响 × 可能性（用于排序，不是精确计算）。

## 2. 架构决策记录（ADR）

### ADR-001：模块化单体 + 独立 Worker，而非微服务

- **状态**：已接受
- **背景**：平台有 10 个引擎、4 种语言运行时。微服务看似「解耦」，但会引入分布式事务、跨服务追踪、部署编排的复杂度。
- **决策**：单一 Rust 进程承载 API + 核心引擎；Python/Java/Node 仅作为**无状态格式转换 Worker**，通过 HTTP/NDJSON 通信，不持有业务状态。
- **后果**：
  - 优点：单事务边界、调试简单、部署一个 compose 即可。
  - 代价：单进程故障影响面大；需要良好的模块边界纪律。
  - 触发拆分条件：单进程无法支撑 > 50 并发分析作业，或团队 > 15 人。
- **替代**：K8s 微服务（拒绝：运维成本远超收益）；Serverless（拒绝：长任务与状态管理不适合）。

---

### ADR-002：PostgreSQL 为唯一权威源，Neo4j 为可重建投影

- **状态**：已接受
- **背景**：Prompt 要求「不能只考虑把所有对象保存到 Neo4j」，且 Provider 必须可替换。
- **决策**：所有实体、关系、属性先写 PG（`graph_meta` schema），通过发件箱异步投影到 Neo4j。Neo4j 删库可重建。
- **后果**：
  - 优点：Provider 可替换；事务一致；许可风险可控；lite 模式可行。
  - 代价：多一份存储；投影延迟（秒级）；需要漂移检测。
  - 必须遵守：禁止任何「只写 Neo4j」的代码路径。
- **替代**：Neo4j 为 SoR（拒绝：锁定 + 许可 + 双写不一致）。

---

### ADR-003：自研 RAG 引擎，只把「检索执行」下推给 Provider

- **状态**：已接受
- **背景**：直接用 RAGFlow 之类会丢失结构语义与证据契约；完全自研又要重写向量检索。
- **决策**：摄取、结构建模、切块、元数据、证据、上下文组装全部自研；`RagProvider` 只负责索引写入与检索执行。
- **后果**：
  - 优点：切块策略可控；证据契约统一；换 Provider 不改业务。
  - 代价：需要自己维护 chunk 生命周期与索引版本。
- **替代**：RAGFlow 作核心（拒绝：变成二次封装，结构语义不可控）。

---

### ADR-004：Analysis Fact 只追加，五态 resolution

- **状态**：已接受
- **背景**：分析结果会随代码、分析器版本变化。覆盖式写入会丢失历史，无法复现。
- **决策**：`code.fact` 只追加；新分析用 `superseded_by` 标记旧记录；每条 fact 带 `resolution / confidence / engine_version / evidence`。
- **后果**：
  - 优点：可复现、可对比、可审计。
  - 代价：存储增长；查询必须带 `valid_to IS NULL` 条件（容易漏，需封装 repository）。
- **替代**：覆盖写入（拒绝：无法回答「三个月前为什么这么判断」）。

---

### ADR-005：Capability 是唯一执行入口

- **状态**：已接受
- **背景**：Agent、MCP、前端、内部用例都需要调用引擎。如果各自直连，权限与审计无法收口。
- **决策**：所有执行经 `Capability Gateway`；网关负责 Schema 校验、权限交集、project_id 注入、预算、超时、审计、输出校验。
- **后果**：
  - 优点：一处收口，越权与注入的防线集中；MCP/Agent/前端共享同一语义。
  - 代价：多一层间接；每个能力要维护 Schema 与版本。
- **替代**：各模块自行暴露（拒绝：权限模型会碎片化）。

---

### ADR-006：AI Provider 双实现，不绑定 Copilot

- **状态**：已接受
- **背景**：Copilot SDK 已 GA 且提供 Rust SDK，但运行时依赖 Copilot CLI sidecar，且需要 GitHub 订阅或 BYOK。企业内网场景不应强制依赖。
- **决策**：`OpenAiCompatProvider` 为默认（DeepSeek / vLLM / Ollama / Azure 兼容端点）；`CopilotRuntimeProvider` 为可选实现，仅在需要其 agent loop 时启用。
- **后果**：
  - 优点：离线可用；不绑定单一厂商；成本可控。
  - 代价：两套实现的工具调用语义需对齐（用统一 `ToolCall` 抽象）。
  - 禁止：反向代理或模拟 Copilot 内部接口。
- **替代**：只用 Copilot（拒绝：内网不可用）；只用自研 HTTP 客户端（会丢掉 Copilot 的 agent loop 能力，但作为默认是合理的）。

---

### ADR-007：日语检索采用「分层词法 + 查询路由」

- **状态**：已接受（2026-11-05 确认）
- **背景**：PostgreSQL 默认全文检索不支持日语；pg_bigm / PGroonga 都需安装扩展。更关键的是，工程现场同时存在两类查询：自然语言（「住所 桁数 チェック」）与部分一致/标识符（「住所チェ」「SALE_CD」），单一方案无法同时覆盖。
- **决策**：
  - **L1 恒开**：Lindera（IPADIC）分词 → `tokenized` 列 → `to_tsvector('simple', tokenized)` + GIN。零扩展依赖，是平台可运行的底线。
  - **L2 条件启用**：检测到 `pg_bigm` 扩展时，对 `chunk.text` 建 GIN（`gin_bigm_ops`），用于部分一致与未登录词。
  - **L3 仅复用**：客户既有 PGroonga 时接入，不作为平台默认依赖。
  - **查询路由**：标识符 / 引号短语 / ≤4 字短输入走 BIGRAM；其余走 TOKENIZED；两路可用时并行并 RRF 融合。响应返回 `lexical_mode`。
- **后果**：
  - 优点：无扩展也能用；有扩展时体验接近专用搜索；索引可按能力降级，不阻塞交付。
  - 代价：两套索引的写入成本；分词器/词典版本必须与索引绑定，换版本需重建；路由规则需要持续调优。
  - 验证：Phase 2 用 60 条金标查询分三类测 recall@10 / MRR / P95，判定规则见 `reference/japanese-search.md` §6。
- **替代**：仅 tsvector（拒绝：部分一致不可用）；默认 PGroonga（拒绝：非 crash-safe、索引约 2.3 倍、扩展审批难）。
- **详见**：`reference/japanese-search.md`。

### ADR-008：影响分析确定性遍历，AI 只做叙述与假设

- **状态**：已接受
- **背景**：让 AI「判断影响范围」不可复现、不可审计，且容易漏项。
- **决策**：影响项由 Rust 图遍历 + 规则打分产生，写入主表；AI 只生成 `narrative` 与 `hypotheses`（标 `INFERRED`，默认折叠，需人工采纳）。
- **后果**：
  - 优点：结果可复现、可解释、可对比。
  - 代价：遍历算法与 hub 处理需要精心设计；长尾影响可能漏（用「未解析清单」弥补）。
- **替代**：AI 主导（拒绝：无法通过审计）。

---

### ADR-009：测试执行采用 JSON 步骤 DSL，而非生成 Playwright 代码

- **状态**：已接受
- **背景**：生成 `.spec.ts` 灵活，但需要沙箱执行任意代码，难以校验，版本升级即失效。
- **决策**：用例以 JSON 步骤描述，由通用 Runner 解释执行；提供受限的 `custom_step` 扩展点（默认禁用）。
- **后果**：
  - 优点：安全、可校验、可版本化、跨 Runner 可移植。
  - 代价：表达能力受限（复杂交互需扩展步骤类型）。
- **替代**：代码生成（在客户明确要求时作为可选模式）。

---

### ADR-010：Workflow 自研，YAML 为唯一语义源

- **状态**：已接受
- **背景**：Dify 是完整应用而非可嵌入引擎；Temporal 运维重且编程模型不同。
- **决策**：Rust 状态机 + YAML 定义；画布是 YAML 的投影，布局存 `x-ui-layout`；编辑产生结构化 patch。
- **后果**：
  - 优点：与 Capability/审批/审计深度集成；部署简单。
  - 代价：复杂流程能力（长时间定时、复杂补偿）需自建。
  - 保留 `WorkflowRuntime` trait，未来可替换。
- **替代**：Temporal（流程数 > 50 且需跨天持久化时重新评估）。

---

### ADR-011：XLSX 自研解析，不依赖 Docling

- **状态**：已接受
- **背景**：日本设计书的 Excel 是「用单元格排版的画布」，Docling 的 XLSX 输出会丢失合并语义、图形对象、公式/缓存值区分。
- **决策**：Rust `calamine` + 直接解析 OOXML（`xl/worksheets`、`xl/drawings`、`xl/sharedStrings`）；Docling 只负责 PDF/DOCX/PPTX。
- **后果**：
  - 优点：单元格级保真；证据可定位到 `Sheet!Range`；无 Python 依赖。
  - 代价：自研工作量大；图表/复杂样式不支持（显式标注）。
- **替代**：Docling 的 XLSX（拒绝：保真度不足）。

---

### ADR-012：前端双图库分工，不互相替代

- **状态**：已接受
- **背景**：关系图与流程图的数据模型、交互范式、性能特征完全不同。
- **决策**：Cytoscape.js 负责关系/依赖/影响图；React Flow 负责 Workflow/Agent/审批流。两者各自封装，不共享状态。
- **后果**：
  - 优点：各用其长；大图性能可控；流程编辑体验好。
  - 代价：两套依赖、两套交互规范、两份维护成本。
- **替代**：统一用一个（拒绝：必然牺牲一类场景）。

---

### ADR-013：Neo4j 锁定 5.26 LTS，查询限定 Cypher 5 子集

- **状态**：已接受（2026-11-05 确认）
- **背景**：用户提出「5.26 LTS 还是 2026.x LTS」。核实后的事实是：**Neo4j 不存在 2026.x LTS**。自 2025 年起采用日历版本（YYYY.MM），每个日历版本只 hotfix 到下一个月度版本发布为止（约 1 个月）；唯一的 LTS 是 5.26（2024-12-06 发布，hotfix 至 2028-06-06），也是 5.x 的最后一个版本。另有 4.4 LTS 已于 2025-11-30 结束支持。
- **决策**：
  1. 基线版本 **5.26.32**，随部署包以独立服务分发（不内嵌、不链接）。
  2. 平台生成的 Cypher **只使用 Cypher 5 语法子集**，不使用 Cypher 25 专有语法，也不写 `CYPHER 25` 前缀。
  3. 2026.x 作为「客户已有则兼容」的目标，不作为基线；CI 门禁跑 5.26，2026.x 仅做兼容性验证。
  4. 升级窗口：2027 H1 评估下一个 LTS；若届时仍无新 LTS，则接受 5.26 至 2028-06 的窗口，并在 2027 Q4 前完成升级方案。
- **后果**：
  - 优点：客户不需要每月升级图数据库；驱动兼容 5.x/6.x；Cypher 5 子集同时能在 2026.x 上跑，切换成本低。
  - 代价：放弃 Cypher 25 的新语法与部分新特性；5.26 不再获得新功能（仅安全补丁）。
  - 风险：2028-06 支持到期前必须完成迁移，列入 `09` Q-08 跟踪。
- **替代**：直接上 2026.x（拒绝：每月升级节奏与私有化交付模式冲突）；Neo4j 4.4（已 EOL）。
