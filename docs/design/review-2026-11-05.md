## B. 规模输入导致的重新基线

新增输入：**设计书 60,000 册（多为 Excel）、Java 13,000 文件、JSP 1,000+**。

原 A-02 的 20 万 chunk 低了两个数量级。第一版重算为 480 万，仍偏低（按 80 chunk/册、20 行一块估）。按设计书常见粒度（8 sheet × 300 行 × 12 列，12 行一块）重算：

| 指标 | 结果 |
|---|---|
| 总单元格 | 17.3 亿 |
| **Embedding chunk（父，12 行块）** | **1,200 万**（上限 2,000 万） |
| **Evidence unit（子，1 行）** | **1.44 亿**（不落库，按需展开） |
| doc_node（Document/Sheet/Section/Region） | 414 万 |
| 向量（1024 维，float32） | 49 GB |
| HNSW 索引 | 75~100 GB |
| PostgreSQL | 2 TB |
| Neo4j | 500 GB（84 万节点 / 500 万边） |
| 首次导入 | 24~48 小时（16 个解析 worker） |

关键修正不是数字，而是三条结构约束：

1. **单元格不建 `doc_node`**。17.3 亿行无法运营。单元格网格压缩后放对象存储，`document_revision.parse_artifact_key` 引用，证据用 `Sheet!Range`。
2. **chunk 不进图**。1,200 万节点对影响分析没有贡献，只压在 Neo4j 上。图只保留 Document / Sheet / 业务实体 / 代码实体。
3. **父子两层 chunk**。只嵌入 12 行左右的父块；1 行的子块用于引用与高亮，不持有 embedding。UI 分开展示「chunk 200 / 引用位置 2,400」。

## D. 审计结论

- 没有「互相矛盾且都自称正确」的残留项。上述 18 项已改为单一事实源。
- 最危险的错误不是数字，而是 **`doc-worker` 与 `docling-serve` 并存**、**chunk 进图**、**单元格建节点** 这三类会在 6 万册规模下直接压垮系统的设计。前两项已修正；第三项已写成硬约束。
- 规模从 20 万 chunk 改为 1,200 万后，**Phase 2 增加 1 周**、**首次导入按 48 小时上限**、**检索 P95 放宽到 2 秒**。这三项必须让客户知道，不能沿用旧承诺。

### F.1 Q-01 的核心设计约束

| # | 约束 | 理由 |
|---|---|---|
| 1 | **不建第二套影响引擎**，只给 ImpactEngine 传 `profile=CHANGE_INQUIRY` | 否则 A-04 与 Q-01 的件数、顺序、风险会不一致 |
| 2 | 必返 `impact_id` | 5 段答案就是同一份 ImpactReport，可下钻到 A-04/A-05 |
| 3 | 自然语言只用于**找种子**，不生成结论 | 避免无根据的断言和伪造引用 |
| 4 | 种子置信度 < 0.7 → `NEEDS_CLARIFICATION`，**不猜** | 猜错目标比答得慢更糟 |
| 5 | 「空」与「取不到」必须分开显示 | 未索引/未解析被读成「无影响」，会直接导致漏改 |
| 6 | 测试只到「放进计划」，**不执行** | 与 D-04（不改代码）和审批模型一致 |
| 7 | `summary` 先出（受入 8s / 目标 3s），其余分块 | 体感取决于第一屏 |
| 8 | 文档段必须游标分页 | 60,000 册，不能一次返回 |

### J.3 实跑暴露的设计缺陷（已修）

**J-1（重要）：DB 角色不能只有一个。** `SELECT … FOR UPDATE SKIP LOCKED` 要求 **UPDATE 权限**。如果 API 和 worker 共用一个角色：

- 给 UPDATE → API 能改写 job 行（越权）

这不是配置问题，是**角色模型缺失**。已补 `detail/02` §0.1：

| 角色 | 权限 | 不给他什么 |

| `systivra_app` | 业务表读写 | `core.job` 的 UPDATE |

| `systivra_scheduler` | `core.job` UPDATE + **BYPASSRLS** | 其他一切 |

`systivra_scheduler` 必须 `BYPASSRLS`：它要跨项目取 job，而 RLS 会把跨项目视野切没。这与 `detail/09` §3 的三进程结构（Scheduler / Runner / Collector）正好对应。

**J-3：`audit_log_id_seq` 的 REVOKE 是无效语句。** 序列只有 USAGE / SELECT / UPDATE 三种权限，`REVOKE DELETE, TRUNCATE` 只会产生警告。已删除该行。

## M. Phase 0 技術検証①：Shift_JIS 判定とバイト偏移（結論：**可**）

### M.1 何を作ったか

`crates/worker/src/text/`（判定・復号・偏移）と `examples/probe_encoding.rs`（実ファイルの確認）。

| 関数 | 役割 |

| `eucjp.java` | EUC-JP | true | 245 | ok |
| `gaiji.java`（髙﨑邉） | Shift_JIS | true | 61 | ok |

`quote` 照合は「先頭 8 文字のバイト範囲を切り出し、同じエンコーディングで戻して一致するか」を見ている。9/9 が ok。壊れたバイト列だけが弾かれた。

速度：debug ビルドで **89ms / 914KB**。全 Java 156 万行（約 125MB）で十数秒。release なら 1 秒台。ボトルネックにならない。

### M.3 途中で分かった重要な事実（設計を 1 つ変えた）

**当初「復号 → 再符号化して元と一致したら偏移を出す」で実装したら、正しい CP932 ファイルが全部 `exact=false` になった。**

原因は CP932 の重複写像。`髙`（U+9AD9）は `0xEEE0` と `0xFBFC` の両方が有効で、`encoding_rs` の再符号化は片方に寄せる。ファイルの中身が正しくても往復が一致しない。

`髙` は日本人名で頻出するので、これは例外ではなく通常ケース。**この方式では実案件の相当割合で偏移が出せなくなる。**

修正：**元バイト列を先頭から歩き、1 文字ずつ「元ファイルで何バイトか」を確定させる**方式に変更。速い道（正規の符号化結果と一致）で大半を処理し、重複写像の文字だけ遅い道（実際のバイト列を復号して長さを探す）に落とす。

修正後は 9/9 が `exact=true`。`detail/06` §4.1.1 に手順を追記した。

### M.4 残る制約と降格案

| 制約 | 影響 | 対応 |
|---|---|---|
| ISO-2022-JP など状態を持つエンコーディングは未対応 | 偏移を出せない | `DecodeError::Unsupported`。実案件ではほぼ出ないが、出たら未解析一覧に出す |
| 1 文字でも長さを決められないと**ファイル全体**の偏移を諦める | そのファイルは行番号のみ | `exact=false`。行番号は本文から数えられるので、証拠は `quote_hash` のみで照合する |
| `confidence` は 0/255 の 2 値 | `detail/06` の「0.75」を数値では表現できない | `chardetng` が数値の信頼度を公開していないため。**2 区間の判定一致**を追加条件にして補った。虚偽の精度を出さないことを優先 |
| 判定は先頭・末尾 64KB | 途中にだけ別エンコーディングが混在するファイルは見逃す | 混在は `had_errors` で落ちる。落ちたものは未解析一覧へ |

### M.5 結論

**可。** 降格不要。`detail/06` の方針（元バイト偏移、信頼度不足は推測しない）はそのまま実装できる。

ただし設計に 1 点修正が入った：**偏移の正しさを「往復一致」で判定してはならない**（M.3）。`detail/06` §4.1.1 に反映済み。

残り 4 つの Phase 0 検証（XLSX 結合セル、JSP の Tree-sitter、OpenRewrite のオフライン classpath、200 冊規模実測）は未着手。

## N. Phase 0 技術検証②：JSP の Tree-sitter 可解析性（結論：**可。ただし設計を 1 つ修正**）

Phase 0 の 2 つ目。1,000+ 本の JSP を解析できるかは Phase 4 全体の前提。

### N.1 実装

`crates/worker/src/jsp/`（マスク・合成・解析）と `examples/probe_jsp.rs`。

| 関数 | 役割 |
|---|---|
| `mask(source)` | JSP 構文を**同じバイト長・同じ改行位置**の空白に置換。Java の文字列リテラル内の `%>` を誤認しない |
| `synthesize(source, blocks)` | scriptlet を出現順に連結し、1 つのメソッドに合成。式は文に包む |
| `analyze(source)` | マスク → HTML 解析 → 合成 → Java 解析 |
| `map_range(segments, s, e)` | 合成ソースの範囲を元ファイルのバイト範囲へ戻す |

### N.2 実測（生成した JSP 5 種、175 ブロック）

| ファイル | HTML エラー | Java エラー | 宣言エラー | ブロック数 |
|---|---|---|---|---|
| `form.jsp`（業務画面、EL 2 箇所） | 0 | 0 | 0 | 7 |
| `logic.jsp`（scriptlet 主体、40 ループ） | 0 | 0 | 0 | 161 |
| `jstl.jsp`（`<c:forEach>` / `<jsp:include>`） | 0 | 0 | 0 | 1 |
| `literals.jsp`（文字列内に `%>`） | 0 | 0 | 0 | 3 |
| `decl.jsp`（`<%! %>` 宣言） | 0 | 0 | 0 | 3 |

マスクは 5/5 でバイト長・改行位置とも不変。プロパティテスト（scriptlet を 200 箇所ランダム挿入）でも位置が動かないことを確認。

**JSTL の `<c:forEach>` や `<jsp:include>` のようなコロン入りタグ名でも HTML grammar はエラーを出さない。** これは事前に懸念していた点で、問題なかった。

### N.3 設計の修正：scriptlet を個別に解析してはならない

最初は素直に「scriptlet 1 つずつを Java grammar に渡す」で実装した。結果は **25% しか通らない**（43/170）。

失敗の理由は 3 つで、どれも JSP の本質：

1. `<% if (user != null) { %>` は**開き括弧だけで閉じていない**。閉じ括弧は別のブロック `<% } %>` にある。
2. `<%= expr %>` は**式であって文ではない**。`request.getContextPath()` を文として並べると Java では不正。
3. `<% for (...) { %>` 〜 `<% } %>` の間に HTML が挟まる。単独では制御構造にならない。

修正：**Jasper などの JSP エンジンと同じく、出現順に連結して 1 つのメソッドへ合成**してから解析する。式は `Object __eN = (式);` に包む。宣言（`<%! %>`）はクラス本体へ別に合成する。

修正後は **5/5 ファイル、175 ブロックすべてエラー 0**。

`detail/06` §4.3 を書き換えた。「scriptlet 内の Java は別途 Java grammar で解析」という 1 行では、実装者が必ず個別解析を書いて失敗する。

### N.4 位置の逆写像

合成すると位置がずれるので、`Segment { synth_start, orig_start, len }` を記録し、AST のノード範囲を元ファイルへ戻す。

ノードの両端が別セグメントにあってもよい。`<% if { %>` から `<% } %>` までのノードは、**間の HTML ごと 1 つの範囲**になる。これは「その if 文が HTML を包含している」という意味的に正しい対応で、影響分析で「この条件分岐がどの表示を左右するか」を出すのにそのまま使える。

### N.5 残る制約

| 制約 | 影響 | 対応 |
|---|---|---|
| EL（`${...}`）は Java ではない | Java 解析の対象外 | HTML 側のテキストとして残す。EL 式の中身を解析する必要が出たら別途 |
| `<jsp:useBean>` などの標準アクション | タグとして扱う。プロパティは取れない | Phase 4 で必要なら属性抽出を追加 |
| タグファイル（`.tag`） | 未検証 | 実案件で使われていれば同じ仕組みで対応可能 |
| 断片の合成が壊れる JSP（極端に不均衡な括弧） | Java 解析が落ちる | エラーノード数で検出し `resolution = PARTIAL` |

### N.6 結論

**可。** マスクと合成の 2 段で、実案件で出る JSP の形は解析できる。

設計に 1 点修正が入った：**scriptlet の個別解析は不可、合成が必須**（N.3）。`detail/06` §4.3 に反映済み。

残り 3 つの Phase 0 検証（XLSX 結合セル、OpenRewrite のオフライン classpath、200 冊規模実測）は未着手。

## O. Phase 0 技術検証③：XLSX の結合セルと図形アンカー（結論：**可**）

60,000 冊の大半が Excel。`detail/01` §5（結合セル）と §7（図形・画像・グラフ）が実装できるかを確かめた。

### O.1 判断：セル読み取りライブラリは使わない

図形・画像・グラフは `xl/drawings/drawingN.xml` にあり、**セル値を読むライブラリの多くはこれを無視する**。図形がどのセルに貼られているかが取れないと、「この入力項目の説明図」を証拠として結び付けられない。

そこで ZIP と XML を直接読む実装にした（`crates/worker/src/xlsx/`、依存は `zip` と `quick-xml` のみ）。

| 関数 | 役割 |
|---|---|
| `open(bytes)` | ZIP を開いてパーツを保持 |
| `sheets()` | `workbook.xml` + rels からシート一覧（**定義順**） |
| `merged_regions(sheet)` | `<mergeCell ref="A1:C3"/>` を読む |
| `figures(sheet)` | `drawing` → rels → `drawingN.xml` のアンカーを読む |
| `MergedRegion::children()` | アンカー以外のセル（値を繰り返さないため。§5） |

### O.2 実測（2 シート / 結合 4 箇所 / 図形 3 種）

```text
sheets=2
[画面定義] merged=3 figures=3 (pic=1 sp=1 chart=1)
  merged A1:F1 anchor=A1 cells=6
  merged A3:A6 anchor=A3 cells=4
  merged C3:E4 anchor=C3 cells=6
  Shape   at G2
  Picture at A7..E15  xl/media/image1.png 33B 7ef27d3d09d0…
  Chart   at C17..I29
[項目一覧] merged=1 figures=0
  merged B2:D2 anchor=B2 cells=3
```

- アンカー変換は正しい（`from` は 0 始まり。`col=6,row=1` → `G2`）
- 画像は `xl/media` の SHA-256 を取得。同じ画像が複数箇所にあってもハッシュで束ねられる
- グラフは種別だけ判定し、系列は取らない（§7 の方針どおり）
- `drawing` パーツが無いシート（項目一覧）は空を返す。異常扱いしない

### O.3 実装中に踏んだ細かい罠

| 罠 | 症状 | 対処 |

| 子孫探索を素朴なスタックで実装 | シート順が逆になる（画面定義が 2 枚目に） | 子を**逆順**に積んで文書順を保つ。テストで固定 |

### O.4 残る制約

| 制約 | 影響 | 対応 |
|---|---|---|
| 実 Excel が吐いたファイルでの確認は未実施 | 生成した OOXML でのみ検証 | 本機に Excel / openpyxl が無い。**顧客の実ファイル 1 冊で必ず再確認する**（Phase 0 の 200 冊実測と同時でよい） |

### O.5 結論

**可。** 結合セルと図形アンカーの両方が、外部ライブラリなしで読める。

ただし **O.4 の 1 行目が重要**：検証は自分で組み立てた OOXML に対してのみ。実 Excel のファイルは共有文字列やスタイルが絡むので、顧客の実物 1 冊で必ず再確認する。
