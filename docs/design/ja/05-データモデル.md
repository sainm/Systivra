# 第 5 部：統一データモデル

## 1. PostgreSQL リレーショナルモデル

### 1.1 Schema 分割

| Schema | 内容 | 特性 |
|---|---|---|
| `core` | ワークスペース、プロジェクト、ユーザー、権限、監査、ジョブ、Outbox | トランザクション中核 |
| `corpus` | 文書、改版、解析木、chunk、ベクトル、証拠 | 読み多・書き少。再構築可能な部分を含む |
| `code` | リポジトリ、改版、ファイル、シンボル、Fact | **追記のみ**。履歴不変 |
| `graph_meta` | Ontology、実体、関係、投影状態 | グラフの正本 |
| `test` | ルール、計画、シナリオ、ケース、データ、実行、被覆 | トランザクション + 大量読み |
| `ai` | Agent、Prompt、実行、承認、Workflow、MCP | 設定 + 実行記録 |
| `ops` | Provider、ヘルス、秘密参照 | 運用手続き |

DB を分けず schema で切る。単一 DB のトランザクションは最大の工学的利点であり、schema は論理境界として機能する。将来の分割にも耐える。

### 1.1.1 システム別の所有権

KB（知識管理）と Impact（影響分析）は同じ DB を使うが、書き込み所有権を分ける。

| データ | 唯一の書き手 | 読み取り |
|---|---|---|
| `core.*` / `ops.*` | 共通カーネル | KB / Impact |
| `corpus.*`（`kb_snapshot` は K4） | KB | Impact は API / 読み取りビュー経由 |
| `code.repository` / `revision` / `source_file` / `symbol` | KB | Impact は読み取りのみ |
| `code.analysis_run` / `fact` / `fact_evidence` | Impact | KB は参照のみ |
| `graph_meta.*` / `test.*` / `ai.*` | Impact | KB は参照しない |

> `code` schema は 1 つだが、内容表（repository / revision / source_file / symbol）と分析表（analysis_run / fact）で書き手が異なる。DB ロールまたは読み取りビューで強制する。詳細は `02-アーキテクチャ.md` §3.2、ADR-016。

### 1.4 索引と分割

| 表 | 方針 | 理由 |
|---|---|---|
| `corpus.chunk` | **`HASH(id)`** で 32〜64 分割。`project_id` はキーにしない | A-02 は単一プロジェクト。`HASH(project_id)` だと全 1,200 万行が 1 区に集中する。UUID ハッシュで均等分散し、FTS / vacuum を分区単位に分割する |
| `corpus.embedding_1024` | **`HASH(chunk_id)`** で同じ分区数に分割し、**分割ごとに HNSW**。`project_id` 列を保持 | 1,200 万 × 1024 次元。単一 HNSW は構築時にメモリ不足。検索は全分区へ並列 fan-out（`detail/03-performance.md` §2） |
| `corpus.doc_node` | Phase 1 は非分区（`revision_id` 索引）。Phase 2 で `revision_id` 分割を検討 | 414 万行。セル単位のノードは含めない |
| `code.fact` | 分割しない。`(project_id, revision_id)` 索引 | 250 万行は単一表で十分。古い revision はエクスポート後に削除 |
| `core.audit_log` | `occurred_at` の月分割 | 保持期間 + ホット/コールド分離 |
| `test.test_execution` | 分割しない | 10 万行規模。180 日でアーカイブ |
| `corpus.evidence` | 分割しない。`document_id` でクラスタ | 証拠検索は常に文書単位 |

### 1.5 保持期間

| データ | 期間 | 削除方法 |
|---|---|---|
| 原本 | 永久（顧客が削除可能） | 論理削除 → 30 日後に物理削除 |
| Chunk / ベクトル | revision に追従 | supersede 後 30 日で GC |
| Fact | 永久 | revision 単位でコールドストレージへ |
| 実行成果物（スクリーンショット/trace） | 180 日 | オブジェクトストレージのライフサイクル |
| 監査ログ | 3 年（設定可） | アーカイブ |
| Agent 実行記録 | 1 年 | アーカイブ |

## 2. Neo4j グラフモデル

### 2.1 ノード

```cypher
(:Entity {
  uid: "8f2c...:a91b...",   // project_id + ":" + entity_id。一意キー
  entity_id: "a91b...",
  project_id: "8f2c...",
  entity_type: "Method",
  name: "update",
  qualified_name: "com.example.UserEditAction#update",
  revision: "def456",
  resolution: "RESOLVED"
})
```

`uid` の単一プロパティに一意制約を置く。複合一意制約やノードキーは Community 版の対応が限られるため避ける。本文・証拠全文・大きな JSON は持たない（PG に置く）。

### 2.2 関係

```cypher
(a:Entity)-[:CALLS {
  rel_id: "uuid",
  resolution: "RESOLVED",
  confidence: 1.0,
  fact_id: "uuid",
  revision: "def456"
}]->(b:Entity)
```

関係型は Ontology 登録簿の固定集合。動的生成は禁止。

### 2.3 制約と索引

```cypher
CREATE CONSTRAINT entity_uid IF NOT EXISTS
FOR (e:Entity) REQUIRE e.uid IS UNIQUE;

CREATE INDEX entity_lookup IF NOT EXISTS
FOR (e:Entity) ON (e.project_id, e.entity_type, e.name);

CREATE INDEX entity_qname IF NOT EXISTS
FOR (e:Entity) ON (e.project_id, e.qualified_name);

CREATE INDEX rel_revision IF NOT EXISTS
FOR ()-[r:CALLS]-() ON (r.revision);
```

関係プロパティ索引は Neo4j 5.x で利用可能。それ以前では削除し、ノード索引主体で走査する。

### 2.4 クエリ雛形（値は必ずパラメータ）

```cypher
MATCH (a:Entity {uid:$uid})-[r]->(b:Entity)
WHERE type(r) IN $rel_types AND r.revision = $rev
RETURN b.entity_id AS id, b.entity_type AS kind, b.name AS name,
       type(r) AS rel, r.resolution AS resolution, r.confidence AS confidence
LIMIT $limit;
```

関係型はパラメータ化できないため、Ontology 登録簿で検証した識別子のみを文字列連結する（`[A-Z_]+` を検査）。

### 2.5 投影状態

```cypher
(:ProjectionState {
  project_id: "uuid",
  last_event_seq: 123456,
  last_event_id: "uuid",
  updated_at: datetime()
})
```

再開位置と漂流検出に使う。

## 3. RAG データモデル（論理）

```text
Document
 ├─ id, project_id, doc_type, title, business_domain, acl_groups
 └─ Revision (1..n)
     ├─ id, source_revision, content_hash, source_encoding, parser, status
     └─ NodeTree
         ├─ node_id, parent_id, node_type, locator, ordinal
         └─ Chunk (1..n)
             ├─ chunk_id, chunk_type, text, token_count, char_count, content_hash
             ├─ locator
             ├─ node_path[]
             ├─ metadata{lang, screen_id, rule_hints[]}
             ├─ embedding[model_id] → vector
             └─ fts tsvector
```

### 3.1 Chunk ID

```text
chunk_id = uuid_v5(
  namespace = project_id,
  name = f"{revision_id}:{locator_canonical}:{content_hash_hex[:16]}"
)
```

内容アドレス方式。同じ内容を再取込しても同一 ID になり冪等。内容が変われば ID も変わり、「同じ ID が別テキストを指す」ことがない。

### 3.2 検索ログ

```sql
CREATE TABLE corpus.retrieval_log (
  id            uuid PRIMARY KEY,
  project_id    uuid NOT NULL,
  query         text NOT NULL,
  query_tokens  text[] NOT NULL,
```

## 4. Analysis Fact Schema

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "schema://fact@1",
  "type": "object",
  "required": ["fact_id","project_id","revision","subject","relation","object",
               "resolution","confidence","analysis_engine","engine_version","evidence"],
  "properties": {
    "fact_id":         { "type": "string", "format": "uuid" },
    "project_id":      { "type": "string", "format": "uuid" },
    "revision":        { "type": "string" },
    "subject":         { "$ref": "#/$defs/entityRef" },
    "relation":        { "type": "string", "pattern": "^[A-Z_]+$" },
    "object":          { "$ref": "#/$defs/entityRef" },
    "resolution":      { "enum": ["RESOLVED","INFERRED","PARTIAL","UNRESOLVED","CONFLICT"] },
    "confidence":      { "type": "number", "minimum": 0, "maximum": 1 },
    "analysis_engine": { "type": "string" },
    "engine_version":  { "type": "string" },
    "evidence":        { "type": "array", "minItems": 1, "items": { "$ref": "schema://evidence@1" } },
    "conflict_group":  { "type": ["string","null"] },
    "unresolved_reason": { "type": ["string","null"] },
    "candidates":      { "type": "array", "items": { "$ref": "#/$defs/entityRef" } }
  },
  "$defs": {
    "entityRef": {
      "type": "object",
      "required": ["kind","key"],
      "properties": {
        "kind": { "type": "string" },
        "key":  { "type": "string" },
        "locator": { "type": ["object","null"] }
      }
    }
  }
}
```

### 4.1 5 状態の意味（固定）

| 状態 | 意味 | 自動判断に使えるか | UI |
|---|---|---|---|
| `RESOLVED` | 解析器が確定。唯一解 | 可 | 実線 |
| `INFERRED` | 根拠のある推論。他の解があり得る | 不可（人手確認） | 破線 + 注記 |
| `PARTIAL` | 部分解析（クラスは分かるがメソッドは不明など） | 不可 | 点線 |
| `UNRESOLVED` | 確定不能 | 不可 | 灰色破線 + 疑問符 |
| `CONFLICT` | 複数由来が互いに排他的 | 不可（裁定必要） | 赤い二重線 |

`confidence` と `resolution` は別物。`INFERRED + 0.95` でも事実として使わない。前者は「どれくらい似ているか」、後者は「確定しているか」。

### 4.2 競合の表現

```json
{
  "conflict_group": "CG-2026-0042",
  "relation": "HANDLES",
  "subject": {"kind":"Screen","key":"USER_EDIT"},
  "candidates": [
    {"kind":"Action","key":"com.example.UserEditAction"},
    {"kind":"Action","key":"com.example.UserEditActionV2"}
  ],
  "resolution": "CONFLICT",
  "unresolved_reason": "struts-config.xml と注釈の指す Action が異なる。移行残骸の可能性"
}
```

競合は利用者に見せる。「正しそうな方を選ぶ」ことをしない。

## 5. Evidence Schema

```json
{
  "$id": "schema://evidence@1",
  "type": "object",
  "required": ["evidence_id","source_type","locator","quote","quote_hash","resolution"],
  "properties": {
    "evidence_id": { "type": "string" },
    "source_type": {
      "enum": ["PDF_PAGE","DOCX_SECTION","EXCEL_RANGE","MARKDOWN_SECTION",
               "CODE_LINE","CONFIG_PATH","TEST_RESULT","CHUNK"]
    },
    "document_id": { "type": ["string","null"] },
    "revision_id": { "type": ["string","null"] },
    "locator":     { "type": "object" },
    "quote":       { "type": "string", "maxLength": 2000 },
    "quote_hash":  { "type": "string" },
    "context_before": { "type": ["string","null"], "maxLength": 300 },
    "context_after":  { "type": ["string","null"], "maxLength": 300 },
    "resolution":  { "enum": ["RESOLVED","INFERRED","PARTIAL","UNRESOLVED","CONFLICT"] },
    "confidence":  { "type": "number" }
  }
}
```

3 つの制約：

1. `quote` は原文の**正確な部分文字列**。サーバーで検証し、一致しなければ拒否（AI の引用捏造を防ぐ）。
2. `locator` はハイライト可能な範囲を特定できること。
3. `quote_hash = sha256(normalize_nfc(quote))`。原文改変の検出に使う。照合は原文（NFC）で行い、NFKC は使わない。
