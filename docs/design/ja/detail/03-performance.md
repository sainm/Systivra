# 詳細設計 03：性能設計（速度）

対象：60,000 冊（大半 Excel）、Java 13,000、JSP 1,000+、embedding chunk 1,200 万。
方針：**受入値（契約）と目標値（チューニング後）を分ける**。受入値は顧客に約束してよい上限、目標値は設計が正しければ届く水準。

---

## 1. SLO（受入値 / 目標値）

| 操作 | 受入値（P95） | 目標値（P95） | P99 | 備考 |
|---|---|---|---|---|
| 検索（ハイブリッド + リランク） | < 2.0s | **< 1.2s** | < 3.0s | 1,200 万 chunk、フィルタあり |
| 文書を開く（1 画面） | < 800ms | < 400ms | < 1.5s | 該当シートのみ描画 |
| 影響分析（6 ホップ） | < 120s | **< 90s** | < 180s | 250 万 Fact、AI 叙述除く |
| グラフ隣接 | < 300ms | < 150ms | < 600ms | 84 万ノード |
| 初回取込（60,000 冊） | < 48h | **< 24h** | < 72h | 受入は 16 ワーカー、目標は 32 ワーカー（§3） |
| 日次増分（100 冊 + 50 Java） | < 40min | < 20min | < 60min | — |
| テスト実行（100 ケース） | < 60min | < 30min | < 90min | 4 ブラウザ並列 |
| API 一覧（50 件） | < 300ms | < 150ms | < 500ms | カーソルページング |

**受入値を超えたら失敗**。目標値に届かない場合は、レイテンシの内訳を出して原因を特定する。感覚で「遅い」と言わない。

## 2. 検索のレイテンシ内訳（1,200 万 chunk）

| 段 | 目標 | 受入 | 主な要因 |
|---|---|---|---|
| クエリ正規化 + 分割 | 5ms | 15ms | Lindera の辞書ロードは起動時のみ |
| クエリ Embedding | 30ms | 80ms | API 往復。ローカル推論なら 10ms |
| ベクトル検索（**64 区 fan-out**） | 60ms | 200ms | 1 区 18〜38 万ベクトル × 25/60ms、並列 16 で 4 波 |
| 全文検索（GIN、64 区 fan-out） | 40ms | 120ms | `ts_rank_cd`、候補 60 件。分区単位で上位を絞ってから合流 |
| pg_bigm（任意） | 30ms | 100ms | recheck の量に依存 |
| RRF 融合 | 3ms | 10ms | 3 リスト × 60 件。分区結果もここでマージ |
| リランク（40 件） | 250ms | 600ms | バッチ 1 回。逐次呼び出しは禁止 |
| 近傍拡張 + 文脈組立 | 30ms | 80ms | 追加 chunk 取得 |
| 合計 | **448ms** | **1,205ms** | 余裕を見て受入 2.0s |

> 各段の受入値を単純合計すると 1,205ms。SLO の 2.0s は、外部 API のテール、GC、同時実行、リランク品質の設定差を含めた余裕値である。合計が SLO を超えたら、まず段ごとの内訳に戻る。

**設計上の要点（重要：pruning に依存しない）**：

- **`project_id` でパーティション pruning は効かない**。A-02 は単一プロジェクト 60,000 冊であり、`HASH(project_id)` なら全 1,200 万行が 1 区に集中する。だから `kb.chunk` は `HASH(id)`、`kb.embedding_1024` は `HASH(chunk_id)` で **32〜64 区へ均等分散**する（`05-データモデル.md` §1.4、`detail/02-database-ddl.md` §6）。
- 速度が出る理由は「1 区だけ見る」ではなく、**「各区が 18〜38 万ベクトルしか持たず、64 区を並列に捌ける」** こと。検索は全分区へ fan-out し、各区の上位 60 件だけを RRF で合流させる。合成後の候補は依然 60 件、リランクは 1 回。
- fan-out の並列度は 16 を起点にする。64 区 ÷ 16 = 4 波。逐次 64 区を回すと受入 2.0s を超えるため**並列は必須**。
- `project_id` は全行の列 + `(project_id, is_current, …)` 索引 + RLS で強制する。partition pruning を防衛線にしない。
- リランクは 40 件を**1 回のバッチ**で送る。40 回の HTTP 呼び出しは 2〜4 秒かかる。
- 全文検索は候補 60 件に制限する。`ts_rank_cd` を全件に計算しない。

## 3. 取込のスループット

| 段 | 速度 | 60,000 冊の所要 | 備考 |
|---|---|---|---|
| Excel 解析 | 5,000 セル/秒/コア | 96h（1 コア、理論） | 17.3 億セル |
| 16 コア（解析のみ） | 80,000 セル/秒 | 6h（理論）→ **12〜24h（実測、IO・失敗対応込み）** | 受入 <48h の根拠 |
| 32 コア（解析のみ） | 160,000 セル/秒 | 3h（理論）→ **6〜12h（実測）** | 目標 <24h の構成 |
| chunk 生成 | 20,000 chunk/秒 | 10 分 | 1,200 万 chunk |
| Embedding（API 200/s） | 200 chunk/秒 | 16.7h | ボトルネック |
| Embedding（バッチ 1,000/s） | 1,000 chunk/秒 | 3.3h | ローカル推論 or 大バッチ |
| HNSW 構築 | 300k ベクトル/区、15 分 | 40 区 × 15 分 = 10h（1 並列）→ **1.5h（8 並列）** | `maintenance_work_mem` 16GB |
| DB 書き込み（COPY） | 50,000 行/秒 | 4 分（chunk） | 行 INSERT は使わない |

**初回取込 end-to-end（受入 16 ワーカー 24〜48h / 目標 32 ワーカー 13〜25h）**：

| 構成 | 解析 + chunk | Embedding | HNSW | その他 | 合計 |
|---|---|---|---|---|---|
| 16 ワーカー（受入） | 12〜24h | 11〜17h | 4〜7h | 再試行 2〜4h | **24〜48h**（並列実行のため合計は単純和ではない） |
| 32 ワーカー（目標） | 6〜10h | 3.3〜8h | 1.5〜3h | 再試行 2〜4h | **13〜25h** |

> 「Excel 解析 12〜24h」は**解析工程だけ**の数字。`detail/01-excel-ingestion.md` §12 と `reference/scale-model.md` §4 も同じ意味で使う。**初回取込（end-to-end）は 24〜48h** であり、両者を混同しない。Embedding と HNSW は解析とパイプラインで重なるため、壁時計時間は各工程の単純和より短い。

**初回取込 24 時間の内訳（32 コア、目標）**：

```text
解析 + chunk 生成   6〜10h
Embedding          3.3〜8h（バッチ次第）
HNSW 構築          1.5〜3h（並列）
DB 書き込み        0.5h
再試行・失敗対応   2〜4h
合計               13〜25h
```

## 4. 影響分析の内訳

| 段 | 目標 | 受入 | 対策 |
|---|---|---|---|
| シード解決（diff → symbol） | 200ms | 1s | tree-sitter はファイル単位でキャッシュ |
| 逆依存 BFS 6 層 | 1.5s | 5s | 層ごとに 1 クエリ、`IN` でバッチ |
| 共有リソース閉包 | 1s | 5s | ハブは展開しない |
| 文書証拠検索 | 3s | 20s | 並列 4、top_k 20 |
| テスト資産照合 | 1s | 5s | インデックスで一括 |
| リスク評点 | 100ms | 500ms | メモリ内 |
| AI 叙述（任意） | 20s | 90s | 予算で打切り |
| 合計（AI 除く） | **7s** | **30s** | 受入 120s は余裕を見た値 |

> AI 叙述、根拠文書の大量取得、ハブ展開を含めると 90s 目標 / 120s 受入。AI は予算（`max_wall_time_sec`）で打ち切り、コア分析を先に返す。

**BFS の実装規約**：

- ノードごとに 1 クエリを投げない。層ごとに `WHERE a.uid IN $uids` でまとめる。
- 辺の取得は `(src_id, rel_type)` / `(dst_id, rel_type)` の索引に当てる。
- 訪問済み集合は Rust 側の `HashSet`。Cypher で `NOT IN` を渡さない。
- 深さ 6 で打ち切る。7 以上は業務的に説明できない。

## 5. 速度を決める 10 の設計判断

| # | 判断 | 効果 | 破った場合 |
|---|---|---|---|
| 1 | **セルを DB 行にしない** | 17.3 億行 → 414 万行 | 取込も検索も不可能 |
| 2 | **chunk をグラフに投影しない** | Neo4j 1,200 万ノード削減 | ページキャッシュ不足で走査が遅い |
| 3 | **`HASH(id)` / `HASH(chunk_id)` で 32〜64 パーティション + パーティション別 HNSW + 並列 fan-out** | ANN 対象 18〜38 万ベクトル/区 | `HASH(project_id)` にすると単一プロジェクトで全行が 1 区に集中し、分割も pruning も効かない |
| 4 | **親 chunk だけ埋め込む** | 1.44 億 → 1,200 万 | Embedding が 1 週間終わらない |
| 5 | **リランクはバッチ 1 回** | 40 回 → 1 回 | 2〜4 秒の固定遅延 |
| 6 | **COPY / バルク INSERT** | 50k 行/秒 | 行 INSERT で 10 倍遅い |
| 7 | **変更ファイルだけ再解析** | 増分が全件の 5〜10% | 毎日 24 時間かかる |
| 8 | **層ごとのバッチ Cypher** | クエリ数 1/100 | N+1 で 30 秒超 |
| 9 | **カーソルページング** | 深いページでも一定 | OFFSET は後半で劣化 |
| 10 | **一覧はサーバー側フィルタ** | 60,000 件を転送しない | 初回表示が 10 秒超 |

## 6. ステージ別の最適化

### 6.1 取込

- ファイル単位で並列。1 ファイル内はシート逐次（メモリ節約）。
- ZIP はストリーム展開。全エントリをメモリに載せない。
- セル格子は `Vec<Cell>` ではなく、行ごとの `SmallVec`。空セルを生成しない。
- chunk 生成は解析と同一プロセスで行い、中間 JSON を書かない。
- DB 書き込みは 5,000 行ごとに `COPY`。1 冊ごとにコミットしない。
- `synchronous_commit=off` は**取込セッションのみ**。落ちたら再取込できることが前提。
- 重複は `content_hash` でスキップ。再取込の 90% を削る。

### 6.2 Embedding

- 64〜256 chunk のバッチ。1 件ずつ呼ばない。
- `content_hash` でキャッシュ。同一テキストは再計算しない（設計書は雛形のコピーが多い）。
- 変更 chunk だけ再計算。`superseded` になった chunk は計算しない。
- ベクトルは `halfvec` を選択肢に。精度が落ちる場合は再ランクで補う。
- API 429 は指数バックオフ。全体を止めない。

### 6.3 索引

- パーティションごとに HNSW を構築。1 本の巨大索引を作らない。
- `maintenance_work_mem=16GB`、`max_parallel_maintenance_workers=4`。
- HNSW は `m=16, ef_construction=64` を起点。recall 不足なら `ef_search` を上げる。
- GIN は `fastupdate=off` で一括構築後に `VACUUM`。
- 索引構築は夜間。構築中も旧索引で検索できる（`index_build` 分離）。

### 6.4 検索

- `hnsw.ef_search=80` を起点。P95 と recall を見て調整。
- **全分区へ fan-out する**。並列度 16 を起点（64 区なら 4 波）。`SELECT … FROM kb.embedding_1024 WHERE project_id = $1 AND model_id = $2` を各分区に並列発行し、分区ごとの上位 60 件だけを返す。逐次 64 区は禁止。
- `project_id` は RLS + `(project_id, is_current)` 索引で絞る。partition pruning を前提にしたクエリを書かない。
- `hnsw.iterative_scan=relaxed_order` でフィルタ後の空振りを防ぐ。
- 全文は `ts_rank_cd` を候補 60 件に限定。分区ごとに上位を絞ってから RRF で合流。
- 同一クエリの結果を 60 秒キャッシュ（プロジェクト + フィルタ + 正規化クエリのハッシュ）。
- 読み取りレプリカを検索に使う（Phase 8）。

### 6.5 グラフ

- Neo4j のページキャッシュは 32GB。84 万ノード / 500 万辺なら全載りする。
- 投影は `UNWIND $batch` で 1,000 件ずつ。1 件ずつ `MERGE` しない。
- 走査は層ごとにバッチ。`MATCH (a)-[r]->(b) WHERE a.uid IN $uids`。
- サブグラフ出力は 5,000 ノードで打ち切る。UI も同時に制限。

### 6.6 フロント

- 一覧は仮想スクロール（50 行ずつ）。全件 DOM を作らない。
- グラフは 800 ノード超で集約表示。3,000 超で Canvas。
- レイアウト計算は Web Worker。
- 画像・スクリーンショットは遅延読み込み。`loading="lazy"`。

## 7. 測定とゲート

| Phase | ゲート | 方法 |
|---|---|---|
| 0 | 200 冊で 5,000 セル/秒/コア、メモリ < 120 B/セル | `criterion` + 実ファイル |
| 2 | 100 万 chunk で検索 P95 < 1.5s、1,000 冊取込 < 2h | k6 + 実データ |
| 4 | Java 13,000 の全解析 < 60 分、増分 < 10% | 実測 |
| 5 | 250 万 Fact で影響 < 120s | 実測 |
| 6 | 100 ケース実行 < 60 分（4 並列） | Playwright |
| 8 | 同時 50 ユーザーで P95 劣化 < 30% | k6 |

**遅いときの調べ方**（順番を固定）：

```text
1. API: X-Response-Time と OTel span で、どの段が遅いか
2. DB: pg_stat_statements で上位クエリ、EXPLAIN (ANALYZE, BUFFERS)
3. 索引: Seq Scan が出ていないか、`(project_id, is_current)` 索引が使われているか、64 区へ並列 fan-out しているか（**プロジェクト pruning は期待しない**。§2）
4. グラフ: PROFILE で db hits、AllNodesScan が出ていないか
5. アプリ: flamegraph で CPU、tokio-console で待ち
6. 外部: Embedding / Rerank / AI のレイテンシと 429
```

## 8. 速度と正確性のトレードオフ

速くするために、次のことは**しない**。

| 禁止 | 理由 |
|---|---|
| 証拠のない結果を返す | P2（証拠優先）に反する |
| 未解析を黙って落とす | P3・P7 に反する |
| 打切りを表示しない | 影響分析の信頼を壊す |
| リランクを黙ってスキップ | `degraded` を必ず返す |
| 古い索引で検索し続ける | `index_build` の状態を UI に出す |

許容する短縮：

- 検索候補を 60 → 40 に減らす（recall を測ってから）。
- リランクを上位 20 件に限定（品質と相談）。
- 影響分析の深さを 6 → 4（UI で明示）。
- AI 叙述を省略（コア分析は出す）。

いずれも**利用者に見える形**で行う。黙って劣化させない。
