## 2. Excel 1 冊あたりの前提

| 項目 | 計画値 | 範囲（実測で置換） |
|---|---|---|
| シート数 | 8 | 3〜15 |
| 使用範囲 | 300 行 × 12 列 | 100〜800 行 |
| セル数 | 28,800 | 5,000〜100,000 |
| 非空セル率 | 35% | 20〜60% |
| 領域（region）数 | 60 | 20〜120 |
| ** embedding chunk 数** | **200** | 120〜400 |
| 平均 chunk テキスト | 1.5 KB | 0.5〜4 KB |
| 行（証拠単位）数 | 2,400 | 800〜6,000 |

> 「設計書 1 冊」はワークブック 1 つを指す。複数シートにまたがる画面定義を 1 冊と数える運用もあるため、**取込時に「文書 = ファイル」で数え、業務単位とは分ける**。

### 2.1 chunk の 2 層定義（重要）

「chunk 数」を 1 つの数字で語ると必ずずれる。本設計では 2 層に分ける。

| 層 | 単位 | 用途 | 保存 |
|---|---|---|---|
| **Embedding chunk（親）** | 12 行前後の表ブロック。ヘッダを繰り返す | ベクトル検索・FTS・リランクの対象 | PG の `corpus.chunk` に保存し、embedding を持つ |
| **Evidence unit（子）** | 1 行、または 1 セル範囲 | 引用・ハイライト・テストデータの根拠 | 原則として行を保存しない。`Sheet!Range` から圧縮 artifact をオンデマンド展開 |

- 親 chunk は 60,000 × 200 = **1,200 万**。
- 子の行は 60,000 × 2,400 = **1 億 4,400 万**。これは「保存する行数」ではなく「引用可能な位置の数」。
- 子をすべて chunk 化すると 1.4 億行になり、埋め込み・索引・vacuum が破綻する。**子は埋め込まない**。

> 「chunk が少ない」と感じる場合、多くは子の粒度を数えている。子は 1 行単位で存在するが、埋め込み対象ではない。この区別を UI でも示す（「チャンク 200 / 引用位置 2,400」）。

## 3. 算出結果

| 指標 | 計算 | 結果 |
|---|---|---|
| 総セル数 | 60,000 × 28,800 | **17.3 億** |
| 非空セル | × 35% | 6.0 億 |
| 領域数 | 60,000 × 60 | 360 万 |
| **Embedding chunk** | 60,000 × 200 | **1,200 万**（上限 2,000 万） |
| **Evidence unit（行）** | 60,000 × 2,400 | **1.44 億**（保存しない） |
| doc_node 数 | 60,000 × (1 + 8 + 60) | 414 万 |
| chunk テキスト | 1,200 万 × 1.5 KB | 18 GB（生） |
| Embedding ベクトル | 1,200 万 × 1024 次元 × 4 B | **49 GB** |
| HNSW 索引 | ベクトルの 1.5〜2 倍 | **75〜100 GB** |
| Java 行数 | 13,000 × 120 | 156 万行 |
| Java メソッド | 13,000 × 8 | 10.4 万 |
| Fact（Java） | 呼び出し 10/メソッド + 読み書き等 | 250 万（上限 500 万） |
| Fact（JSP） | 1,200 × 120 | 14 万 |
| グラフ entity | 文書 60,000 + シート 480,000 + コード 200,000 + 業務 100,000 | **84 万**（chunk / region を含めない） |
| グラフ edge | entity の 4〜6 倍 | 350〜500 万 |

**重要な帰結**：

- 埋め込み対象は 1,200 万。当初前提（20 万）の **60 倍**。単一 HNSW 索引ではメモリが足りない。
- セルを 1 ノードにすると 17.3 億行。**セル単位の doc_node は作らない**。
- 行をすべて chunk にすると 1.44 億行。**子はオンデマンド展開する**。
- chunk をグラフに投影すると 1,200 万ノード。**chunk はグラフに入れない**。

## 5. 設計への強制変更

### 5.1 セルを DB 行にしない

- `doc_node` は **Document / Sheet / Section / Region** まで。セルは作らない。
- セル格子は解析成果物として **圧縮してオブジェクトストレージ**（Parquet または gzip JSON）に置き、`document_revision.parse_artifact_key` で参照する。
- chunk は描画済みテキストを持ち、必要なら artifact の該当範囲を再読する。
- 理由：17.3 億行は PostgreSQL でも Neo4j でも運用できない。証拠位置は `Sheet!Range` で足りる。

### 5.2 chunk をグラフに投影しない

- グラフは Document / Sheet / 業務実体 / コード実体まで。
- chunk は PG の `corpus.chunk` に留め、RAG の証拠として使う。
- 理由：1,200 万ノード + 辺は、影響分析に寄与しない割に Neo4j のメモリとバックアップを圧迫する。

### 5.3 chunk と embedding を分割する

- `corpus.chunk` は **`HASH(id)`**、`corpus.embedding_1024` は **`HASH(chunk_id)`** で **32〜64 パーティション**へ均等分散する。**`project_id` をパーティションキーにしてはならない**。A-02 は単一プロジェクト（60,000 冊）なので `HASH(project_id)` は全 1,200 万行を 1 区に集中させ、分割も pruning も機能しない。
- 両者とも UUID のハッシュなので、分区数を揃えれば同一 chunk の `text` と `vec` は同じ番号の分区に入る（結合時の局所性）。
- `project_id` は全行の列として保持し、`(project_id, is_current, …)` 索引と RLS でスコープを強制する。**プロジェクト pruning は使わない**。検索は全分区へ並列 fan-out し、各区 18〜38 万ベクトルの ANN 結果をマージする（`detail/03-performance.md` §2）。
- **パーティションごとに HNSW** を張る。単一索引に 1,200 万ベクトルを入れると、構築時のメモリと vacuum が破綻する。

### 5.4 取込はバッチ前提

- 60,000 本を 1 本ずつアップロードさせない。**マニフェスト（CSV/JSON）+ 一括取込ジョブ**を用意する。
- 重複は `content_hash` で排除。改版は `document_revision` で積む。
- 失敗ファイルは一覧化し、部分成功を許す。全体を失敗にしない。
- 進捗は「ファイル数 / セル数 / chunk 数」の 3 指標で出す。ファイル数だけでは終盤で止まって見える。

### 5.5 一覧 UI はサーバー側ページング前提

- 60,000 件の文書ツリーを一括で返さない。ノード単位の遅延読み込み。
- 検索とフィルタはサーバー側。クライアントで全件ソートしない。
- 文書詳細は「ページ / シート / 領域」単位で開く。1 冊を丸ごとレンダリングしない。

| Object Storage（解析成果物） | 1〜2 TB | 圧縮セル格子 + 抽出テキスト |

| バックアップ | 4 TB | PG 日次 + オブジェクト差分 |

## 9. 検証計画（Phase 0 で実施）

1. 実案件から **200 冊**を抽出（シート数・セル数・領域数・行数の分布を取る）。
2. 1 冊あたりのセル数、非空率、region 数、**embedding chunk 数と行数**を実測。
3. 5,000 セル/秒/コアが現実か、メモリピークと共に測定。
4. 1,000 冊を 16 ワーカーで流し、1 冊あたりの所要時間と失敗率を測る。
5. 実測値で本稿の係数を置換し、`08-実装計画.md` の受入値を更新する。

**判定**：1 冊平均が 28,800 セルを大きく超える場合（例：100,000 セル）、初回取込は 48 時間を超える。その場合は「取込対象を年度・業務域で分割する」運用を顧客と合意する。

|---|---|---|---|
| S-01 | 1 冊あたりのセル数が想定の 3 倍 | サンプル平均 > 80,000 セル | 取込を段階分割。UI で進捗と優先度を提示 |

| S-06 | 行を chunk 化したくなる要求 | 「1 行 1 chunk で検索したい」 | 子はオンデマンド展開。埋め込みは親のみ。UI で 2 層を明示 |
