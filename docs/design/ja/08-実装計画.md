# 第 8 部：実装計画

## 1. 基本方針

1. **各 Phase はエンドツーエンドで動く経路を必ず持つ**。「今回はバックエンドだけ、画面は次期」を認めない。受入時に使えるか判断できない。
2. **まず貫通、次に深化**。Phase 1 で 1 つの PDF を「アップロード → チャンク → 検索 → 証拠」まで通す。以降は置き換えと強化であり、ゼロからの作り直しではない。
3. **不確実性を前倒し**。最も転ぶ 4 件（XLSX 解析、OpenRewrite のオフライン型解決、JSP 解析、Shift_JIS の文字コード）は Phase 0 / 2 / 4 の前半で技術検証する。失敗したら方式を変える。結合テストまで待たない。

### 1.1 体制（2026-11-05 確定）

| 役割 | 人数 | 備考 |
|---|---|---|
| Rust バックエンド | 2 | 1 名はアーキテクト兼務 |
| フロントエンド | 1 | Phase 1 から |
| テスト / QA | 0.5 | Phase 5 から 1 |
| 設計 | 0.5 | 最初の 8 週に集中 |
| Java（OpenRewrite Worker） | 0.5 | Phase 4 に集中 |

以下はこの体制での見積り。人数が変われば比例調整するが、**依存順は変えない**。

> **工期の対外口径（2026-11-05 改訂）**：Phase 0〜7 の合計は **32 週**（0:2 + 1:4 + 2:5 + 3:4 + 4:5 + 5:3 + 6:5 + 7:4）。Phase 2 を 4→5 週に延ばした分を反映済み。Phase 8（運用引渡し・SSO・HA）は終了時期を定めず、顧客要件で別途見積もる。**旧口径の 31 週は使わない**。

### Phase 2：RAG Engine 完成（5 週）

| モジュール | 範囲 |
|---|---|
| XLSX | 自作：sheet / セル / 結合 / 数式 / 図形アンカー / 名前付き範囲。領域検出とチャンク |

**受入**

- embedding モデル切替時、旧索引も検索可能（`index_build` 分離）。新索引完成後に切替。
- 3 分類それぞれ recall@10 ≥ 0.85（平均で弱点を隠さない）。

### Phase 5：Impact Analysis（3 週）

| モジュール | 範囲 |
|---|---|
| 変更セット | Git diff / 手動 / 文書改版 / DDL diff |
| シード解決 | ファイル + 行 → シンボル。フィールド変更 → 読み書きメソッド閉包 |
| 走査 | 逆依存、データ流、共有リソース閉包、hub 打切り |
| 証拠 | 文書 RAG + コード Fact + グラフ経路の統合 |
| リスク | 決定論的評点 + 因子内訳 |
| 出力 | ImpactReport（JSON / Markdown）、影響グラフ |
| **単独問合せ** | **Q-01 変更影響問合せ**（`profile=CHANGE_INQUIRY`）。5 セクション + 分割 SSE + `NEEDS_CLARIFICATION`。テストは既存ケースのみ（`detail/08`） |
| フロント | A-04 三欄ワークベンチ、A-05 詳細、経路の可視化、**Q-01（5 ブロック）** |

**受入**

- SAMPLE の 20 変更で、影響項目の recall 90% 以上、precision 70% 以上（人手の正解と比較。過剰包含は理由を明示）。
- 任意の影響項目で経路と証拠を展開可能。証拠のない項目が 0。

**受入**

- SAMPLE の 300 ルールから 900 組以上のデータを生成。人手抽検で有効率 80% 以上。

- **100 ケースを 4 並列で 60 分以内**（`detail/09` R-01）。失敗時の成果物 4 点（画像 / DOM / console / trace）が出る。

- 被覆スナップショットが再計算可能（同じ test_run で同じ数値）。
- 「生成したが未実行」は被覆 0 とし、UI に明記。
- **Q-01 の「テスト」に草稿・手順・データ境界が出る**。草稿は最大 20 件、`status=DRAFT`。承認は人間だけ。Q-01 から実行はできない。

### 3.1 なぜ 13 crate で、20 ではないか

| 当初案 | 扱い | 理由 |
|---|---|---|
| `ontology` | `engine-graph` に統合 | グラフの型体系であり結合が強い。分けると循環依存 |
| `audit` | `store` に統合 | 追記専用表 + 照会。独立 crate は転送層を増やすだけ |
| `provider-core` + `provider-manager` | `providers` に統合 | trait と登録簿が相互参照し、境界が曖昧 |
| `capability-contracts` | `contracts` に統合 | 契約は集中管理し、生成と版管理を一元化 |
| `application` | `app` として独立 | api と worker が共用するため |

判定：**ある crate のコンパイルが 90 秒を超える、または公開 API が単独リリースできるほど安定したとき**に分割する。それ以外は `pub use` を増やすだけ。

## 4. 依存順と開発順

### 4.1 コンパイル依存

```text
domain ──▶ contracts ──▶ store ──▶ providers ──▶ engines ──▶ runtime ──▶ app ──▶ api
                                                                    └──▶ worker
```

`engine-impact` は `engine-graph` + `engine-rag` に依存。`engine-test` は `engine-code` + `engine-impact` に依存。これが Phase 順のハード制約。

### 4.2 Phase 内の開発順

```text
1. 契約（Schema / trait / migration）
2. ストア層 + 単体テスト
3. エンジン中核 + 単体テスト（合成データ。実案件に依存しない）
4. Capability 包装 + 統合テスト（testcontainers）
5. API + OpenAPI
6. フロント（先に mock、API 後に切替）
7. E2E + 正解集
8. ドキュメントと ADR 更新
```

手順 3 が重要。エンジンは実データを待たずに開発する。例：影響エンジンは 200 ノードの合成グラフで走査と評点を作り、Phase 4 後に実グラフへ差し替える。

### 4.3 並行できるもの

| 並行 | 説明 |
|---|---|
| Phase 2 フロント と Phase 3 バックエンド | トレーサビリティ画面はグラフ API 前に mock で作れる |
| Phase 4 Java Worker と Rust スキャナ | NDJSON 契約で分離。同時開発可能 |
| Phase 6 テスト DSL と Phase 5 影響 | Runner は case schema だけ必要 |

## 5. SAMPLE プロジェクト

### 5.1 仕様

| 項目 | 数 | 備考 |
|---|---|---|
| 画面 | 24 | 一覧 8 / 登録編集 8 / 参照 4 / バッチ 4 |
| 業務モジュール | 6 | ユーザー、受注、在庫、申請、承認、通知 |
| Java クラス | 約 180 | Action 24、Service 30、Dao 40、Form 24、Validator 15、Util 20、他 |
| JSP | 60 | カスタム tag 3 種を含む |
| DB 表 | 42 | 主外部キー、ビュー 3、ストアド 2 |
| 検証ルール | 300+ | 単項目 180、項目間 60、業務 60 |
| 設定 | 5 種 | web.xml、struts-config、dicon、Spring bean、MyBatis mapper |
| 設計書 | 6 冊 | 基本設計 PDF、詳細設計 XLSX（12 sheet）、画面設計 XLSX、API 仕様、DB 定義、テスト仕様 |
| 版 | 3 revision | 影響分析と diff のデモ用 |

### 5.2 必ず含める「難しい」要素

- Struts1 形式 Action + `struts-config.xml`
- SAStruts 注釈形式（Struts1 と混在。移行残骸を模し `CONFLICT` を作る）
- Seasar2 Dicon + S2JDBC
- JSP カスタム Tag（`<my:input>`）+ taglib
- 反射呼び出し（`Class.forName` 1 件）
- 文字列連結 SQL（2 件。`UNRESOLVED` を作る）
- 動的プロキシ（Spring AOP 風）
- 項目間検証（開始日 < 終了日）
- 複数表トランザクション（受注 + 在庫 + 申請）
- 外部 API 呼び出し
- 日本語特有入力（全角、外字、サロゲート）
- **文字コード混在**：Java は UTF-8、JSP は Shift_JIS、CSV は Windows-31J

## 6. テスト戦略

| 層 | ツール | 対象 | 目標 |
|---|---|---|---|
| 単体 | `cargo nextest` + `proptest` | 領域規則、走査、評点、チャンク | 行 75% 以上、中核アルゴリズム 90% 以上 |

### 6.1 正解集（Golden Set）

| 正解集 | 規模 | 注釈 | 用途 |
|---|---|---|---|
| RAG | 60 問（3 分類 × 20） | 正解 chunk_id 集合 | recall@10、MRR、証拠正確率 |
| コード解析 | 200 関係 + 30 動的 | 真の関係、期待 resolution | precision / recall |
| 影響分析 | 20 変更 | 人手の影響一覧（理由付き） | recall、precision、打切り率 |

正解集はコードと共にコミットし、CI で毎回実行。閾値超の低下はマージをブロックする。

### 6.2 性能目標（Phase 2 / 4 で実データにより校正）

> 下表は**受入値（顧客に約束してよい上限）**。設計が正しければ届く目標値は `detail/03-performance.md` §1 を参照（検索 1.2s、影響 90s、初回取込 24h）。

| シナリオ | 受入値（P95） | 条件 |
|---|---|---|
| 検索 P95 | < 2.0s | 1,200 万 chunk、ハイブリッド + リランク |
| 隣接 P95 | < 300ms | 84 万ノード、1 ホップ |
| 影響分析（6 ホップ） | < 120s | 250 万 Fact、37 項目 |
| PDF 解析 | 20 ページ/秒 以上 | テキスト層あり |
| Excel 解析 | 5,000 セル/秒/コア 以上 | 結合 + 数式 |
| 初回取込 | < 48 時間 | 60,000 冊、16 ワーカー |
| 日次増分 | < 40 分 | 100 冊 + Java 50 ファイル |
| 増分コード解析 | 全件の 10% 未満 | 1 ファイル変更 |

## 8. マイルストーン・リスク

| 時期 | 最大リスク | 兆候 | 代替案 |
|---|---|---|---|
| Phase 2 末 | Excel 解析品質不足 | 30 領域抽検で 60% 未満 | 「sheet 単位チャンク」に降格し明示。Phase 5 前に補完 |
| Phase 4 中 | OpenRewrite オフライン不可 | classpath 構築失敗 30% 超 | 全面構文レベルに降格。`PARTIAL` 明示。型解決を顧客環境の前提条件に |
| Phase 4 末 | JSP 解析の位置ずれ | 証拠行のずれ 2 行超 | ファイル単位の位置に退避。精度より正確性 |
| Phase 5 | 影響項目の爆発（数百件） | 単回 200 件超 | hub 閾値の引き締め + 業務領域の事前絞り込み + 段階表示 |
| Phase 6 | Playwright のセレクタ不安定 | 初回合格 40% 未満 | `data-testid` 規約。顧客への埋込み依頼 |
| Phase 7 | Copilot SDK が企業網で不可 | CLI 起動失敗 | OpenAiCompatProvider のみで運用。Copilot は任意 |
