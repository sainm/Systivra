# 第 8 部：実装計画

## 1. 基本方針

1. **各 Phase はエンドツーエンドで動く経路を必ず持つ**。「今回はバックエンドだけ、画面は次期」を認めない。受入時に使えるか判断できない。
2. **まず貫通、次に深化**。Phase 1 で 1 つの PDF を「アップロード → チャンク → 検索 → 証拠」まで通す。以降は置き換えと強化であり、ゼロからの作り直しではない。
3. **不確実性を前倒し**。最も転ぶ 4 件（XLSX 解析、JSP 解析、Shift_JIS の文字コード、プロジェクト内シンボル索引による多候補解決）は Phase 0 / 2 / 4 の前半で技術検証する。失敗したら方式を変える。結合テストまで待たない。

### 1.1 体制（2026-11-05 確定）

| 役割 | 人数 | 備考 |
|---|---|---|
| Rust バックエンド | 2 | 1 名はアーキテクト兼務 |
| フロントエンド | 1 | Phase 1 から |
| テスト / QA | 0.5 | Phase 5 から 1 |
| 設計 | 0.5 | 最初の 8 週に集中 |

以下はこの体制での見積り。人数が変われば比例調整するが、**依存順は変えない**。

> **工期の対外口径（2026-11-05 改訂）**：Phase 0〜7 の合計は **32 週**（0:2 + 1:4 + 2:5 + 3:4 + 4:5 + 5:3 + 6:5 + 7:4）。Phase 2 を 4→5 週に延ばした分を反映済み。Phase 8（運用引渡し・SSO・HA）は終了時期を定めず、顧客要件で別途見積もる。**旧口径の 31 週は使わない**。

### Phase 4：Code Analysis（5 週）

> 2026-11-07 の実装状況は [`docs/phase4/acceptance.md`](../../phase4/acceptance.md)。
> `DIR` / `SNAPSHOT` / `GIT`、元バイト偏移、Java / JSP / XML / SQL、Fact、増分、
> API / UI の source-only 縦断実装と指定性能受入は PASS。SVN は未導入。
> OpenRewrite / 顧客 classpath と解析による 250 万 Fact 生成は外部依存として
> 受入境界の外に置く。型解決は ADR-017 により対象外である。

| モジュール | 範囲 |
|---|---|
| リポジトリ同期 | Git / ディレクトリ / スナップショット。revision と tree digest |
| 走査 | 言語判定、ignore、増分（hash + diff）。**文字コード判定と変換、元バイトオフセット保持** |
| Tree-sitter | Java / JS / TS / HTML / CSS / JSON / SQL（ベストエフォート）。シンボルと単純呼び出し |
| XML | quick-xml：web.xml、struts-config.xml、dicon、Spring bean、MyBatis mapper |
| JSP | ハイブリッド：等長プレースホルダ → HTML 解析 → scriptlet / EL / tag 復元 |
| プロジェクト内シンボル索引 | 同一 revision の class / method / field 索引。型・名前・引数数で照合し、複数候補は `INFERRED` |
| Framework Adapter | Struts1 / SAStruts / Seasar2(S2JDBC) / Spring MVC / MyBatis / カスタム Tag |
| SQL | Rust 内の限定 SQL 解析：表・列参照、文種別 |
| Fact | 統一モデル、5 状態、競合グループ、増分 supersede |
| フロント | コード解析概要、依存グラフ、未解析一覧 |

**受入**

- SAMPLE 案件：クラス / メソッド認識率 98% 以上。メソッド呼び出しの precision 98% 以上（`RESOLVED` 辺）。
- 反射 / 動的プロキシ 30 件がすべて `INFERRED` または `UNRESOLVED`。`RESOLVED` と誤記されたものが 0。
- 増分：1 ファイル変更で再解析が全件の 10% 未満。
- プロジェクト内で一意に解決できれば `RESOLVED`、複数候補または外部型なら `INFERRED / UNRESOLVED` とし、`RESOLVED` を偽装しない。

> SCIM Users / Groups とグループ→ロール、ユーザー管理画面、SIEM 転送を追加した。
> SAML / 真の HA / 本番 WAL 常時転送は未実装。

マルチテナント、SSO（SAML/OIDC）、詳細 RBAC、バックアップ復旧訓練、性能最適化、セキュリティ強化、HA 配置、運用マニュアル。終了時期は定めず、顧客要件で優先順位を決める。

### 3.1 なぜ 13 crate で、20 ではないか

| 当初案 | 扱い | 理由 |
|---|---|---|
| `ontology` | `engine-graph` に統合 | グラフの型体系であり結合が強い。分けると循環依存 |
| `audit` | `store` に統合 | 追記専用表 + 照会。独立 crate は転送層を増やすだけ |
| `provider-core` + `provider-manager` | `providers` に統合 | trait と登録簿が相互参照し、境界が曖昧 |
| `capability-contracts` | `contracts` に統合 | 契約は集中管理し、生成と版管理を一元化 |
| `application` | `app` として独立 | api と worker が共用するため |

判定：**ある crate のコンパイルが 90 秒を超える、または公開 API が単独リリースできるほど安定したとき**に分割する。それ以外は `pub use` を増やすだけ。

### 3.2 単一プロジェクト前提と KB の段階分割

本製品は特定の JavaWeb プロジェクト 1 件を対象とし、マルチテナント / 二製品化は行わない（ADR-015）。したがって `knowledge_base` エンティティや共有カーネルの製品分割は追加しない。既存の 13 crate 構成と `project` スコープをそのまま使う。`project` は 1 行だが、RLS の防御線として残す。

#### KB の段階分割

| 段階 | 範囲 | バージョン管理 | 対応 Phase | 状態 |
|---|---|---|---|---|
| K1 文書基礎 | PDF、検索、証拠 | `document_revision`、CURRENT / SUPERSEDED、`evidence.revision_id` | Phase 1 | 完了 |
| K2 日本語設計書と検索品質 | XLSX / DOCX / PPTX、文字コード / 外字、Lindera / pg_bigm、構造 chunk、親子 chunk、一括取込 | 改版履歴 UI、版指定検索、`index_build`、モデル切替 | Phase 2 | 実装済み（受入は `docs/phase2/acceptance.md`） |
| K3 コード | Java / JSP / XML / SQL、Fact、コードと文書のリンク | `code.revision`、diff、Fact の supersede | Phase 4 | source-only 正式受入 PASS（Git、13k、2.5M Fact、Neo4j） |
| K4 版集合と横断追跡 | cross-doc / code impact | KB snapshot、as-of 検索、release 比較 | Phase 5 | source-only 正式受入 PASS（20変更、SSE/PDF、2.5M edge 6-hop） |

- 版管理は K1 から必須。K1 は原本 revision、K2 は索引版と履歴 UI、K3 はコード版、K4 は KB snapshot を追加する。
- KB snapshot は K4 の着手前に DDL を確定する。現行 DDL には含めない。
- 版を指定しない検索は CURRENT / `is_current` を既定とする。
- 各段階は既存 Phase に対応させ、独立した第 2 ロードマップは作らない。

> KB と Impact の分担は `02-アーキテクチャ.md` §3.2 / ADR-016。KB の K1〜K4 と Impact の Phase 3〜5 を既存 Phase で進め、2 本目の取込 / 解析 / 検索パイプラインは作らない。

## 4. 依存順と開発順

### 4.1 コンパイル依存

```text
domain ──▶ contracts ──▶ store ──▶ providers ──▶ engines ──▶ runtime ──▶ app ──▶ api
                                                                    └──▶ worker
```

`engine-impact` は `engine-graph` + `engine-rag` に依存。`engine-test` は `engine-code` + `engine-impact` に依存。これが Phase 順のハード制約。

> 本製品は単一プロジェクト前提のため、カーネル / プロダクトの分割は行わない（ADR-015）。`project` は 1 行だが、RLS の防御線として残す。

### 4.2 Phase 内の開発順

```text
1. 契約（Schema / trait / migration）
2. ストア層 + 単体テスト
3. エンジン中核 + 単体テスト（合成データ。実案件に依存しない）
4. Capability 包装 + 統合テスト（testcontainers）
5. API + OpenAPI
6. フロント（先に mock、API 後に切替）
7. E2E + 正解集
8. ドキュメントと ADR 更新
```

手順 3 が重要。エンジンは実データを待たずに開発する。例：影響エンジンは 200 ノードの合成グラフで走査と評点を作り、Phase 4 後に実グラフへ差し替える。

|---|---|

### 6.1 正解集（Golden Set）

| 正解集 | 規模 | 注釈 | 用途 |
|---|---|---|---|
| RAG | 60 問（3 分類 × 20） | 正解 chunk_id 集合 | recall@10、MRR、証拠正確率 |
| コード解析 | 200 関係 + 30 動的 | 真の関係、期待 resolution | precision / recall |
| 影響分析 | 20 変更 | 人手の影響一覧（理由付き） | recall、precision、打切り率 |

正解集はコードと共にコミットし、CI で毎回実行。閾値超の低下はマージをブロックする。

### 6.2 性能目標（Phase 2 / 4 で実データにより校正）

> 下表は**受入値（顧客に約束してよい上限）**。設計が正しければ届く目標値は `detail/03-performance.md` §1 を参照（検索 1.2s、影響 90s、初回取込 24h）。

| シナリオ | 受入値（P95） | 条件 |
|---|---|---|
| 検索 P95 | < 2.0s | 1,200 万 chunk、ハイブリッド + リランク |
| 隣接 P95 | < 300ms | 84 万ノード、1 ホップ |
| 影響分析（6 ホップ） | < 120s | 250 万 Fact、37 項目 |
| PDF 解析 | 20 ページ/秒 以上 | テキスト層あり |
| Excel 解析 | 5,000 セル/秒/コア 以上 | 結合 + 数式 |
| 初回取込 | < 48 時間 | 60,000 冊、16 ワーカー |
| 日次増分 | < 40 分 | 100 冊 + Java 50 ファイル |
| 増分コード解析 | 全件の 10% 未満 | 1 ファイル変更 |
