## 3. 選定理由

### 3.1 なぜ Rust を中核にするか

| 理由 | 具体 |
|---|---|
| 決定論的計算が中心 | 影響走査、Fact 正規化、増分 diff は CPU/IO 集約で、遅延の予測可能性が必要。GC 停止がない |
| 単一バイナリ配布 | オンプレで「ランタイムを大量にインストール」を避けたい。イメージを 100MB 未満にできる |
| 資源効率 | 同規模で JVM の 1/3〜1/5 のメモリ。顧客の内網 VM は概して小さく、メモリが制約になる |
| 型で契約を表す | Capability の入出力、Provider の能力宣言を型で表現できる |
| Worker との境界 | Rust が編成・正規化・計算、Python/Java/Node は形式変換のみ。責務が滲まない |

**代償**：開発速度は Python より遅い。文書解析・NLP の生態系は Python に劣る。採用コストも高い。したがって「形式解析」と「日本語分割」は成熟部品に委ね、Rust で無理に書き直さない。

### 3.2 データストア

| 選択 | 理由 | 却下した代替 |
|---|---|---|
| PostgreSQL を SoR | トランザクション、JSONB、全文、ベクトル、行レベルセキュリティが 1 エンジンに揃う。PITR が成熟 | MongoDB（tx が弱い）、MySQL（pgvector/JSONB が弱い） |
| pgvector | ベクトルとメタデータが同庫。権限・revision フィルタ・JOIN を SQL に押し下げられる | Qdrant / Milvus（別サービス、別ネットワーク往復、DB 間整合性） |
| Neo4j を投影に限定 | Cypher の経路表現が自然。可視化生態系が成熟 | NebulaGraph（運用が重い）、JanusGraph（性能・活発度） |
| MinIO | S3 互換。顧客は任意のオブジェクトストレージに替えられる | ローカル FS（複数インスタンス・版管理が不可） |

**pgvector の制約（設計に明記）**：

1. `vector(N)` の次元は列型で固定。**次元の異なるモデルを同じ表に置けない**。次元ごとに表を分け（`embedding_768` / `1024` / `1536`）、同一表内のモデルは **partial HNSW index**（`WHERE model_id = $1`）で分離する。クエリに `model_id` がないとインデックスに当たらない。
2. HNSW 構築はメモリを食う。`maintenance_work_mem` 不足で劣化する。大規模案件の再構築は別枠で計画する。
3. フィルタ + ANN の recall 問題：`SET LOCAL hnsw.iterative_scan = relaxed_order` が必須。そうでなければ「このプロジェクトだけ」で候補が空になる。

**大規模時の追加制約（A-02：embedding chunk 1,200 万）**：

- 1,200 万 × 1024 次元 × 4 B = 49 GB。HNSW 索引は 75〜100 GB。単一索引は構築時のメモリが足りない。
- **`project_id` はパーティションキーにしない**。A-02 は単一プロジェクト 60,000 冊であり、`HASH(project_id)` では全 1,200 万行が 1 区に集中して分割が意味を失う。`kb.chunk` は `HASH(id)`、`kb.embedding_1024` は `HASH(chunk_id)` で **32〜64 パーティション**へ均等分散し、パーティションごとに HNSW を張る。
- `project_id` は全行に列として保持し、`(project_id, is_current, …)` 索引と RLS でスコープを強制する。**プロジェクト pruning ではなく索引 + RLS が防衛線**。検索は全分区へ並列 fan-out し、各区 18〜38 万ベクトルの ANN 結果をマージする（`detail/03-performance.md` §2）。
- `halfvec` でベクトルを半分にし、再ランクで精度を補う選択肢を残す。
- この規模の検索 P95 は **受入上限 2.0 秒 / 目標 1.2 秒**（`detail/03-performance.md` §1）。`reference/scale-model.md` §8 は受入値の一覧。

**日本語コーパスに対する Embedding / Rerank の要件**：

- Embedding は**日本語で評価**して選ぶ（bge-m3 系の多言語モデルなど）。英語 benchmark で代用しない。意味検索の品質はここで決まり、後段の語彙ルーティングやリランクでは救えない。
- Rerank も日本語対応が必須。英語専用の reranker は正解を下位に落とし、リランクしないより悪化する。
- 評価集は実在の日本語設計書から作る。機械翻訳した英語サンプルでは、敬体/常体、カタカナ外来語、主語省略の表現をカバーできない。

### 3.3 コード解析

| 層 | 技術 | 他を使わない理由 |
|---|---|---|
| 構文 | tree-sitter | 増分解析、誤り許容、多言語 API。ANTLR は言語ごとの文法記述と誤り回復が弱い |
| 意味（Java） | OpenRewrite LST | 型解決・メソッド解決・ファイル横断シンボルがある。JavaParser は型解決なし、Spoon は完全な classpath と大きなメモリを要求 |
| 設定 | quick-xml | Tree-sitter に **XML grammar がない**（F-04）。ストリーム処理で位置情報を保持 |
| SQL | JSqlParser（Java Worker 内） | tree-sitter の SQL grammar は第三者製で方言が不安定。JSqlParser の方が Oracle/PostgreSQL 方言に実用的 |
| JSP | 自作ハイブリッド | 利用可能な grammar がない。HTML として解析し、`<% %>` / `${}` / `<jsp:include>` を領域として切り出して個別処理 |

**OpenRewrite の利用境界**：

```text
可：Java ソースの LST 解析、型解決、メソッド呼び出し解決、継承/実装、注釈抽出
不可：recipe の実行、Code Genome Project への依存、OpenRewrite 実行系の製品組込み
```

型解決には classpath が必要。閉域顧客では依存 jar を事前収集（`mvn dependency:build-classpath` など）し、`classpath_index` として保存する。**classpath がない場合は構文レベルに降格し、ファイル横断関係をすべて `PARTIAL` とする**。解析成功のふりをしない。

### 3.4 文書解析

| 形式 | 方式 | 理由 |
|---|---|---|
| XLSX | 自作（calamine + OOXML） | 日本の設計書は「表」ではなく「セルで組んだキャンバス」。結合セル、行高/列幅、図形アンカー、数式とキャッシュ値、定義名、コメントを保持する必要がある |
| PDF | docling-serve | レイアウト解析、読み順、表構造、OCR。自作は非現実的 |
| DOCX | docling-serve | 節構造 + 表 |
| PPTX | docling-serve | 図文混在。スライド番号と図形位置を保持 |
| HTML | Rust ネイティブ（scraper） | 構造が明確。外部サービス不要 |
| MD / TXT / CSV | ネイティブ | — |

**XLSX に必須の項目**：

```text
workbook.sheets[]        → シート名、索引、可視性、順序
sheet.dimension          → 使用範囲
cells[r][c]              → 値、型、数式、スタイル ID、コメント
merged_ranges[]          → 結合範囲（値は左上のみ。展開が必須）
drawings[]               → 図形/画像/グラフ。アンカーセル + オフセット
defined_names[]          → 名前付き範囲（印刷範囲など）
hyperlinks[]             → 内外リンク
row_heights / col_widths → 視覚的なグルーピングの判断材料

禁止：
  sheet を 1 本のテキストに平坦化する
  結合セルの従属関係を捨てる
  数式の計算結果だけを値として扱う（数式自体も情報）
```

**文字コードの前提**：顧客コーパスは UTF-8 と限らない。JSP / Java / SQL / CSV で Shift_JIS / Windows-31J が混在する。すべてのテキスト入口で `chardetng` による判定と `encoding_rs` による変換を行い、証拠位置のために元バイトオフセットを保持する。信頼度 0.75 未満は `ENCODING_UNDETECTED` とし、推測しない。

### 3.5 AI Provider

| 実装 | 用途 | 制約 |
|---|---|---|
| `OpenAiCompatProvider` | **既定**。DeepSeek、vLLM、Ollama、Azure OpenAI 互換 | `/chat/completions` + tools のみ。構造化出力は JSON Schema + 再試行検証。`response_format` の全面対応を仮定しない |
| `CopilotRuntimeProvider` | 任意。agent loop（ファイル編集、MCP、hook）が必要な場合 | Copilot CLI プロセスに依存。GitHub 購読または BYOK が必要。**内部 API の逆プロキシは禁止** |

能力宣言は Provider が自己申告する。

```rust
pub struct AiCapabilities {
    pub streaming: bool,
    pub tool_calling: bool,
    pub parallel_tool_calls: bool,
    pub json_schema_output: bool,
    pub vision: bool,
    pub max_context_tokens: u32,
    pub max_output_tokens: u32,
}
```

能力欠如は**明示的降格**：`json_schema_output=false` なら「プロンプト制約 + 解析失敗時の再試行 + 失敗ならエラー」。成功したふりをしない。

### 3.6 フロントエンド

| 選択 | 役割 | 理由 |
|---|---|---|
| React + TS + Vite | アプリ基盤 | 生態系、採用面。Vite の起動が速い |
| Tailwind + shadcn/ui | デザインシステム | shadcn は「プロジェクトにコピーする」部品。深く改造できる |
| TanStack Query | サーバー状態 | キャッシュ、無効化、楽観更新、ジョブ進捗ポーリング |
| Zustand | クライアント状態 | グラフの選択・フィルタ・レイアウトなど局所状態 |
| Cytoscape.js | 関係図 | 大規模グラフ、レイアウト、サブグラフ出力。D3 で自作しない |
| React Flow | フロー図 | ノードが React コンポーネント。フォームを埋め込める。関係図には使わない |
| Monaco | コード/diff | VS Code と同源。diff ビューが標準で使える |

## 4. 却下した選択肢

| 案 | 却下理由 | 再検討条件 |
|---|---|---|
| 中核を Python / Java | Prompt が Rust を要求。Python は高並行編成と長いトランザクションに追加設計が必要 | 再検討しない |
| 最初からマイクロサービス | 体制と運用能力に合わない。分散 tx、追跡、配置が進捗を食う | 単一プロセスで 50 並行ジョブを捌けない時 |
| Kafka / NATS | 初期は PG job 表で十分（SKIP LOCKED で数千/秒）。中間設備が増える | 500 ジョブ/秒超、または拠点間 |
| Elasticsearch | 日本語分割に結局プラグインが要る。クラスタが増える。PG の権限・tx と分断される | 複雑な関連度調整やログ検索が必要な時 |
| LangChain / LlamaIndex を中核に | 「糊」でありエンジンではない。分割戦略・証拠契約・権限フィルタは自前で制御する必要がある | 再検討しない |
| Dify を Workflow に | 完全アプリであり組込みエンジンではない。データモデルと UI に固定される | 自作 Workflow を断念した場合 |
| Temporal | 強力だが運用が重い。初期フローは単純 | フローが 50 本超、かつ日をまたぐの永続化と複雑な補償が必要な時 |
| Neo4j を SoR に | 02 §4.2 参照 | 再検討しない |
| Tree-sitter で XML | 公式 grammar がない（F-04） | 成熟した grammar が現れた時 |
| 自作 Python Docling Worker | `docling-serve` が安定 HTTP API を提供。車輪の再発明 | マッピングをアダプタ層で吸収できない時 |

## 5. リスクと互換性

| # | リスク | 症状 | 緩和 |
|---|---|---|---|
| T-01 | sqlx 0.9 と 0.8 の API 差 | マクロ、型マッピング、プール設定の変更 | Phase 1 第 1 週で固定し ADR 化。nightly 機能は使わない |
| T-02 | Tree-sitter grammar の ABI 不一致 | 0.27 runtime で 0.23 grammar が panic / 無言失敗 | runtime と grammar を厳密固定。CI に「全 grammar がサンプルを解析できる」スモークテスト |
| T-03 | OpenRewrite のオフライン型解決失敗 | 依存解決できず構文レベルに降格 | 明示降格 + `PARTIAL`。顧客側で classpath 事前生成。`classpath_complete` を結果に記録 |
| T-04 | Docling の性能 | PyMuPDF の 5〜30 倍遅い。大 PDF で数分 | 解析予算 + タイムアウト + ページ並列。テキスト層 PDF は高速パス |
| T-05 | Neo4j ライセンス | Community は GPLv3。リンク・改変・配布すると自社コードに波及 | 独立サービスとして配布。リンク・改変・組込みをしない。法務が Phase 1 で確認 |
| T-06 | pgvector の次元・モデル切替 | 旧ベクトルと混用 | `embedding_model` 登録簿 + 次元別表 + 索引版。切替は再構築ジョブ |
| T-07 | 日本語辞書のライセンス | IPADIC / UniDic で条件が異なる | 初期は IPADIC。UniDic は法務確認まで使わない |
| T-08 | Playwright のオフライン | ブラウザバイナリの取得が必要 | 同梱イメージ + `PLAYWRIGHT_BROWSERS_PATH` |
| T-09 | フロント依存の急速な更新 | 半年で文書の版が古くなる | 版を書かない。lockfile + 四半期の更新窓 |
| T-10 | Rust の Office 解析の隙間 | 図形・グラフ・複雑なスタイルの抽出に OOXML 手書きが必要 | 初期は「セル + 結合 + 図形アンカー + 数式」に限定。グラフ内容は `UNSUPPORTED` と明示 |

## 6. 依存ガバナンス

| 規則 | 実行方法 |
|---|---|
| すべての依存を固定 | `Cargo.lock` / `pnpm-lock.yaml` / docling イメージ tag / Maven `dependencyManagement` |
| `*` 版の禁止 | CI 検査 |
| ライセンスホワイトリスト | Apache-2.0 / MIT / BSD / PostgreSQL License / EPL-2.0 は可。GPL/AGPL は法務評価、かつ独立サービス形のみ |
| セキュリティスキャン | `cargo audit` + `pnpm audit` + Trivy。high/critical でブロック |
| 更新リズム | 四半期ごとに更新窓。セキュリティパッチは随時。メジャー更新は ADR 必須 |
