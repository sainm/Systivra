# 第 1 部：製品定位

## 1. 一文での定位

> **設計書・ソースコード・データベース・テストを同じ証拠グラフ上に置き、改修の影響範囲を「計算・検証・監査」できるようにする。**

Systivra は、企業のレガシーシステム保守を対象とした**ソフトウェアエンジニアリング分析・テスト自動化基盤**である。文書 Q&A ボットでも、コードスキャナでもない。「**事実 + 証拠 + 関係 + 閉ループ**」を提供する基盤である。

| 限定 | 意味 | 対極 |
|---|---|---|
| 追跡可能 | すべての結論が「どの設計書の何ページ / どのセルの範囲 / どのファイルの何行目」に戻れる | 出典のない自然言語だけを返す |
| 計算可能 | 影響範囲とカバレッジは決定論的アルゴリズムで算出。AI は説明と仮説のみ | AI の印象で「影響がありそう」と列挙する |
| 閉ループ | テスト資産は影響分析から派生し、カバレッジは**実行結果**で判定 | 「ケースを生成した」ことを「カバーした」と呼ぶ |

## 2. 利用者

| 役割 | 典型的な像 | 本当の要求 | 提供するもの | 主な入口 |
|---|---|---|---|---|
| **PM / 保守運用責任者**（橋本・45 歳） | 改修案件を 3 件並行。顧客から毎週「今回はどれくらいか、他に影響はないか」と聞かれる | 影響範囲と工数の根拠。説明責任を果たせること | 影響分析レポート（階層 + 証拠 + リスク）、回帰範囲 | プロジェクト概要 / 影響分析 / 帳票出力 |
| **上流 SE / 業務アナリスト**（田中・38 歳） | 基本設計・詳細設計を書く。業務は分かるがコードは読めない | この業務ルールはどこに書かれ、実装されているのか | 業務ルール ↔ 設計書 ↔ 実装のトレーサビリティ | 設計書検索 / トレーサビリティ / ルール一覧 |
| **開発・保守エンジニア**（佐藤・32 歳） | 15 年前のシステムを引き継ぎ、変更前に 2 日かけてコードを読む | このメソッドを変えると誰が困るか。このテーブルは他に誰が書いているか | 呼び出し連鎖、逆依存、共有リソースの利用者 | コード分析 / 依存グラフ / 影響グラフ |
| **テスト責任者 / QA**（鈴木・41 歳） | 検証ルールが 1000 件超。Excel で管理。回帰は経験で選ぶ | 何をテストすべきか、十分か、証明できるか | ルール一覧、テストデータ生成、実行結果、カバレッジ | テスト計画 / カバレッジ / 実行ダッシュボード |
| **アーキテクト / 品質管理者**（山本・50 歳） | 監査・顧客品質レビューに晒される | このツールの結論は信頼できるのか | 解決状態の分布、信頼度、Provider 能力マトリクス、監査ログ | プラットフォーム管理 / 監査 / 分析履歴 |

> 設計上の意味：**同じデータを 4 つの語り口で見せる**。PM には「影響 7 画面・業務ルール 3 件・リスク中」、エンジニアには「呼び出し辺 14 本・反射 2 件未解決」、QA には「ケース 23 件追加・うち 9 件実行済み」と見える。データは 1 つで、投影が 4 つある。

## 3. 中核シナリオ

### S1 改修影響調査（主シナリオ）

顧客要求：「住所チェックを全角漢字・数字のみ、長さ 20 → 30 に変更」。エンジニアは Validator 1 メソッドと JSP の `maxlength` を変えた。

プラットフォームが答えること：

1. 実際に変わったファイル・メソッド（決定論：diff → シンボル特定）
2. この検証メソッドの呼び出し元（逆 `CALLS`、間接含む）
3. どの画面がこの検証を通るか（`Screen → Action → Service → Validator`）
4. どの業務ルール文書が記述しているか（RAG + エンティティリンク、ページ付き）
5. DB カラム長と整合するか（`Column.length=20` の決定論的検出）
6. 同じテーブルに書いている箇所は他にあるか（共有リソース閉包）
7. 既存テストのうちどれがこの画面をカバーしているか
8. **確定できない箇所**（反射、動的プロキシ、文字列連結のメソッド名）
9. リスク等級と推奨回帰範囲

成果物：`ImpactReport`（構造化 JSON + グラフ + Markdown/PDF）。各項目に `path` / `evidence` / `resolution` / `confidence` を付与。

### S2 レガシー構造の理解

新規引き継ぎで設計書がない。コードと設定から再構築する。

- 画面一覧（JSP + Action マッピング + `web.xml` / Dicon）
- 実際の呼び出し関係（「あるべき論」ではなく「解析できた事実」）
- データアクセス全景（どの Service がどのテーブルを読み書きするか）
- デッドコード・孤立画面（入辺のない Action）
- **未解析一覧**（「分からない」を明示する。推測しない）

価値：「2 週間コードを読む」を「2 時間図を見る + 半日検証」に短縮。

### S3 設計書 Q&A と証拠追跡

「この項目はなぜこの検証なのか」「この画面の項目定義はどこか」に、**位置情報付き**で答える。

- Excel：`Sheet / セル範囲` まで
- PDF：`ページ + ブロック`
- Word：`節`
- コード：`ファイル:行`

さらに「文書にはこう書かれている」「コードはこう実装している」「両者が矛盾（CONFLICT）」を区別する。

### S4 テスト資産の派生と回帰閉ループ

`ImpactItem → TestScenario（正常 / 異常 / 境界）→ TestCase（実行可能な手順）→ TestData（同値類 + 境界）→ Playwright 実行 → TestResult → Coverage`

制約：**Case は実行できなければならない**。実行できないものは「テストアイデア」として別管理し、カバレッジに算入しない。

### S5 検証ルールの棚卸し（1000 件の現実）

Java / JSP / JavaScript から検証ルールを抽出し、`ValidationRule` として管理する。

| 項目 | 例 |
|---|---|
| rule_id | `RULE-USER-ADDR-001` |
| source | `UserEditAction.java:128` / `user_edit.jsp:74` |
| field | `住所` |
| type | `LENGTH` / `REQUIRED` / `PATTERN` / `RANGE` / `CROSS_FIELD` |
| condition | `全角 && length <= 20` |
| valid / invalid / boundary | `東京都…` / `ABC` / `20 文字ちょうど` |
| evidence | 詳細設計書 `画面項目定義!C12` |

1000 ルールは約 3000〜5000 件のテストデータに対応する。手作業は不可能。ルールから自動生成し、人間の修正を許容し、修正履歴を残す。

## 4. 業務ループ

```text
   要件・設計資料 ──┐
   ソースコード   ──┼─→ ① 知識構築 ──→ ② 関係構築 ──→ ③ 影響分析
   DB / 設定      ──┤   (RAG/Chunk)      (Graph/Fact)      (Impact)
   テスト資産     ──┘                                        │
          ↑                                                  ↓
          │                                          ④ テスト設計
          │                                        (Plan/Scenario/
          │                                         Case/Data)
          │                                                  │
          └──── ⑦ 学習・改善 ←── ⑥ 被覆判定 ←── ⑤ 実行・記録
                (Feedback)        (Coverage)      (Playwright)
```

7 段のうち、**AI が深く関与してよいのは ③ と ④ のみ**。残り 5 段は決定論的プログラムである。これが信頼性の源泉であり、「AI テスト生成器」との本質的な差である。

閉ループの判定条件：

> 1 回の変更について、人手の補足説明なしに「影響項目 → 対応ケース → 実行結果 → カバレッジ結論」の連鎖を出力でき、各段に証拠が付くこと。1 つでも切れれば閉ループではない。

## 5. 他の 3 種ツールとの違い

| 観点 | 一般的な RAG | コード分析ツール | テスト管理ツール | **Systivra** |
|---|---|---|---|---|
| 基本単位 | Chunk（テキスト断片） | ファイル / シンボル | ケース / 欠陥 | **Entity + Fact + Evidence** |
| 構造の保持 | 弱い（分割で失う） | 強い（AST/LST） | なし | **強い（文書木 + コードシンボル + 表座標）** |
| 関係の表現 | ベクトル類似度 | 呼び出し / 継承 | なし | **型付き関係。出典と解決状態付き** |
| バージョン | 通常なし | ブランチ単位 | なし | **結論ごとに revision を固定。再現可能** |
| 信頼度 | 測れない | 規則内で確定 | 人手判定 | **RESOLVED / INFERRED / PARTIAL / UNRESOLVED / CONFLICT の 5 状態** |
| 横断追跡 | なし | なし | 弱い（手作業） | **文書 ↔ コード ↔ DB ↔ テストの 4 方向** |
| テスト閉ループ | なし | なし | 資産はあるが派生しない | **影響項目からケースを派生し、実行結果で被覆を再計算** |
| 主な失敗 | もっともらしいが出处がない | きれいな図が業務に通じない | 書いたケースが腐る | **解析不足を隠さず明示する** |

### 5.1 RAG との違い：証拠契約

一般的な RAG の出力は「文章 + 文書名」である。Systivra の出力は `Evidence` 構造：

```json
{
  "evidence_id": "EV-7f3a...",
  "source_type": "EXCEL_CELL_RANGE",
  "document_id": "DOC-0012",
  "revision_id": "REV-0007",
  "locator": { "sheet": "画面項目定義", "range": "C12:F12", "row": 12 },
  "quote": "住所：全角20文字以内。未入力時エラー",
  "chunk_id": "CH-9a1c...",
  "resolution": "RESOLVED",
  "confidence": 1.0
}
```

3 つの絶対規則：

1. **locator のない証拠は登録しない**。解析できなければ `UNRESOLVED`。「第 3 章あたり」は許さない。
2. **引用はジャンプできる**。クリックで原文を開き、該当範囲をハイライトする。
3. **証拠にバージョンがある**。文書改版後、古い結論は `stale` とし、黙って無効化しない。

### 5.2 コード分析ツールとの違い：業務意味層

jQAssistant / Spoon / JavaParser は `A calls B` を教えてくれる。しかし次は分からない。

- `B` がどの業務ルールに対応するか
- そのルールが詳細設計書のどこに書かれているか
- どの画面がそれを起動するか
- 変更時にどのテストを実行すべきか

Systivra のコード分析の成果物は「図」ではなく、**統一 Fact Model に入る事実**である。文書エンティティ・テスト資産と同じグラフに載って初めて価値になる。

同時に誠実であるべき点：**コード解析は 100% 完全にはならない**。反射、動的プロキシ、文字列連結 SQL、JSP カスタムタグ、JavaScript の動的挙動。これらは `INFERRED` または `UNRESOLVED` とし、「なぜ確定できないか」を添える。100% 正確だと主張する呼び出しグラフは、82% と明示されたグラフより危険である。

### 5.3 テスト管理ツールとの違い：登録ではなく派生

| | テスト管理ツール | Systivra |
|---|---|---|
| ケースの出所 | 人が書く | 影響項目 / 業務フロー / 検証ルールから派生し、人が修正 |
| 要件との関係 | 手作業でタグ付け | グラフ上の辺。証拠付き |
| カバレッジの意味 | 実行率 | **要件 / ルール / 画面 / 影響項目の 4 次元。実行結果のみ認定** |
| 変更後の動作 | 人が無効ケースを判断 | 影響分析が対象ケースを自動で示す |
| データ生成 | 手入力 | 検証ルールから同値類・境界値を生成。追跡可能 |

## 6. 製品原則（レビュー時の判定基準）

| 原則 | レビューで問う一言 |
|---|---|
| P1 決定論優先 | プログラムで計算できる結論を、なぜ AI に任せるのか |
| P2 証拠優先 | この結論をクリックして原文が開くか。開かないなら公開しない |
| P3 不確定を明示 | 解析できない箇所を、UI は利用者に伝えているか |
| P4 再現可能 | 3 か月後に同じ revision で再実行して、同じ結果になるか |
| P5 差し替え可能 | Neo4j を別製品に替えて、業務コードは何行変わるか（答えは 0 でなければならない） |
| P6 AI なしで動く | すべての AI Provider を止めて、どこまでできるか（① ② ③ ⑤ ⑥ は必須） |
| P7 完全と偽らない | 「未解析」件数は画面に出ているか。隠すのは欺瞞である |

## 7. 非目標

1. **IDE にはしない**。エディタは閲覧と diff のみ。補完はしない。
2. **CI/CD 基盤にはしない**。既存パイプラインと接続し、テスト資産と結果を扱う。
3. **汎用チャットボットにはしない**。すべての対話はプロジェクト文脈と能力ホワイトリストに縛る。
4. **初期はコードを自動修正しない**。提案 patch まで。確定は顧客側（A-07）。
5. **汎用 BI にはしない**。可視化はエンジニアリング分析に限定する。
6. **コード品質スコアは出さない**。複雑度・重複率は取り込めても、「点数」は説明不能である。
7. **顧客間の知識共有はしない**。プロジェクト分離はハード制約（A-10）。

## 8. 成功判定

| 指標 | 目標 | 測定方法 |
|---|---|---|
| 影響調査の所要時間 | 2 人日 → 2 時間以内 | 実案件での作業時間比較 |
| 影響項目の recall | 90% 以上（人手基準） | 実変更 20 件で人手の影響一覧を正解として比較 |
| 影響項目の precision | 70% 以上（根拠ある過剰包含は許容） | 同上。過剰は理由を明示 |
| 証拠の到達率 | 結論の 95% 以上が原文にジャンプ可能 | evidence 200 件を人手検証 |
| 未解析の明示率 | 100%（黙って捨てない） | `UNRESOLVED` が UI に出ているか |
| テスト資産の実行可能率 | 派生ケースの 60% 以上がそのまま実行可能 | 初回実行の合格率 |
| 回帰カバレッジ判定の正確率 | 85% 以上 | 実際の欠陥漏出と照合 |
