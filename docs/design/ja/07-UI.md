# 第 7 部：UI 設計

## 1. 定位

**Modern Developer Workbench + Engineering Intelligence Workspace**。ERP の管理画面にはしない。

3 つの主張：

1. **情報密度優先**。企業案件の価値は細部にある。1 画面に 20 行見える方が 8 行より有用。余白は装飾ではなくグループ化に使う。
2. **分析過程を見せる**。読み込みは回転アイコンではなく「128/240 ファイルを解析中」。待ち時間と停止の判断ができる。
3. **証拠が手元にある**。結論の横から原文を開ける。別画面に飛ばして戻れなくしない。

- 「0 件」と「未解析で出せない」を**別の文言・色**で出す。
- テストのボタンは「計画に入れる」まで。**実行ボタンを置かない**（D-04）。
- 詳細な契約・速度・降格は `detail/08-change-inquiry.md`。

## 4. 可視化

### 4.1 分担（固定境界）

| ライブラリ | 用途 | ノード規模 | レイアウト | やらないこと |
|---|---|---|---|---|
| **Cytoscape.js** | Ontology、依存、影響、追跡 | 10〜5,000 | dagre / cose-bilkent / 独自階層 | フォーム、フロー編集 |
| **React Flow** | Workflow、Agent、承認 | 5〜80 | 手動 + 自動整列 | 大規模関係分析 |

混用の結果：Cytoscape でフロー編集は苦痛（カスタムノード UI が弱い）、React Flow で 5,000 ノードは固まる。

### 4.2 Cytoscape の操作規約

| 操作 | 挙動 |
|---|---|
| ホバー | 1 ホップ隣接をハイライト。他は透明度 0.15 |
| 単クリック | 選択 + 右詳細更新（追加リクエストなし。既読データ） |
| ダブルクリック | 次層を展開（増分リクエスト、スケルトン） |
| 右クリック | 中心にする / 隠す / この経路だけ / ID コピー |
| 矩形選択 | 一括操作（テスト範囲に追加 / サブグラフ出力） |
| 検索 | ヒットをパルス表示 + 中央寄せ |
| レイアウト切替 | dagre（階層）/ cose（クラスタ）/ 同心円（影響階層） |

視覚符号：

| 次元 | 符号 |
|---|---|
| 実体型 | 形状（円 = クラス/メソッド、四角 = 画面、菱形 = 表、六角 = 業務ルール）+ 色 |
| 解決状態 | 線種（実線 = RESOLVED、破線 = INFERRED、点線 = PARTIAL、灰破線 = UNRESOLVED、赤二重 = CONFLICT） |
| 影響方向 | 辺の色（上流 = 橙、下流 = 青、共有 = 紫） |
| リスク | ノードの外枠太さ |
| 打切り | 外枠の破線 + 「+N」バッジ |

**色だけで状態を区別しない**。形状と線種を同時に変える。

### 4.3 性能

- 800 ノード超：集約表示（Package / Module で折り畳み）。展開時に遅延読み込み。
- 3,000 ノード超：アニメーション無効、Canvas レンダラ。
- レイアウト計算は Web Worker。
- 増分描画。全体再描画をしない。

## 5. インタラクション

| 機能 | 規約 |
|---|---|
| コマンドパレット | `⌘K`（Phase 2）。画面遷移、実体検索、操作実行（権限内） |
| ジョブセンター | 右上に常設（Phase 2）。実行中を表示。ドロワーで展開。他の操作を阻害しない |
| 通知 | 「人の判断が要る」ものだけ（承認、失敗、漂流警報）。進捗は通知しない（Phase 2） |
| テーマ | 明 / 暗。システム追従。両テーマでコントラストを検証 |
| 密度 | 表は「標準 / 高密度」切替（Phase 2）。ユーザー設定に保存 |
| ショートカット | `G then I` で影響分析、`/` で検索フォーカス、`Esc` でドロワー閉 |

### 5.1 状態設計（全画面で定義）

| 状態 | 要件 |
|---|---|
| 読み込み | スケルトン + 段階文言（「解析中 128/240」）。全画面スピナーにしない |
| 空 | 「なぜ空か」+ 次の行動（「設計書が未取込」+「取込」ボタン） |
| エラー | コード + 人語 + 再試行 + trace_id（コピー可） |
| 部分失敗 | 成功部分 + 失敗一覧。全体エラーにしない |
| 権限不足 | 不足権限と申請先を示す。空白画面にしない |
| 打切り | 「結果を打ち切った（理由：深さ / 予算 / ハブ）」と明示し、絞り込み導線を出す |

### 5.2 フォームと編集

- 長いフォームは分割（ケース編集：基本 → ステップ → データ → 証拠 → レビュー）。
- 破壊的操作は二段確認。**リソース名の入力**を要求する（「OK」だけにしない）。
- 下書き自動保存（5 秒 or フォーカスアウト）。「保存済み 12:03」を表示。
- 未保存で離脱する場合は警告。

### 5.3 アクセシビリティ

- WCAG 2.1 AA。フォーカス可視。全操作がキーボードで可能。
- グラフには「表形式」の代替ビュー（スクリーンリーダーは図を読めない）。
- コントラスト 4.5:1 以上（本文）、3:1 以上（大字・図形境界）。

## 6. 日本語 UI の原則

「翻訳」ではなく「日本企業の業務ソフトの作法に合わせる」。

### 6.1 文体

| 場面 | 文体 | 例 |
|---|---|---|
| ラベル・見出し | 体言止め | 「影響範囲」「未解析項目」 |
| 説明・ヘルプ | です・ます | 「この操作は取り消せません。」 |
| エラー | 簡潔な断定 + 対処 | 「設計書を読み込めませんでした。ファイル形式を確認してください。」 |
| 確認ダイアログ | 結論先出し | 「この影響分析を削除しますか？削除すると元に戻せません。」 |

避ける：過剰な敬語（「させていただきます」の連発）、直訳調（「あなたのプロジェクト」）、英語直搬（「サブミット」→「登録」）、感嘆符と絵文字。

### 6.2 用語統一（開発前に確定）

| 概念 | 日本語 | 禁止 |
|---|---|---|
| Project | プロジェクト | 案件、PJ（UI では使わない） |
| Screen | 画面 | スクリーン、ページ |
| Design doc | 設計書 | ドキュメント（汎称のみ） |
| Impact | 影響範囲 | インパクト |
| Traceability | トレーサビリティ | 追跡可能性 |
| Coverage | カバレッジ | 網羅率、被覆率（混用禁止） |
| Unresolved | 未解析 | 不明、エラー |
| Evidence | エビデンス | 証拠（法的すぎる） |
| Scenario | シナリオ | シーナリオ |
| Test case | テストケース | テスト項目（混同しやすい） |

用語集は `docs/ui/glossary-ja.md`。CI で禁止語を検査する。

### 6.3 表記

| 項目 | 規則 | 例 |
|---|---|---|
| 日付 | `yyyy/MM/dd` | `2026/11/05` |
| 日時 | `yyyy/MM/dd HH:mm` | `2026/11/05 20:02` |
| 年度 | 4 月始まり、`2026年度` | 会計年度の集計 |
| 数値 | 半角、3 桁区切り | `1,234` |
| 割合 | 整数 + `%`、小数第 1 位まで | `82.4%` |
| 金額 | `¥1,234,567`（半角） | — |
| 単位 | 半角スペース区切り | `12 件` `3.4 秒` |
| 括弧 | 全角 `（）` 日本語 / 半角 `()` 英語・コード | — |
| 句読点 | `、` `。` | `,` `.` は使わない |
| カタカナ | 全角。長音を省略しない | `コンピューター`（JIS 規則で統一） |
| 英字 | 半角。固有名詞は原綴り | `Playwright` `Neo4j` |

### 6.4 レイアウトとタイポグラフィ

| 項目 | 値 | 理由 |
|---|---|---|
| 本文 | 14px / 行間 1.7 | 日本語は行間を広めに取らないと詰まる |
| 表内 | 13px / 行間 1.5 | 情報密度 |
| 補助 | 12px | 単位・注記 |
| 見出し | 16 / 20 / 24px | — |
| フォント | `Noto Sans JP`（本文）、`BIZ UDPGothic`（代替）、`JetBrains Mono`（コード） | 商用可、Web 配信可、等幅で日本語コメントも崩れない |
| 最大行長 | 全角 40 文字程度 | それ以上は読まれない |
| 禁則処理 | 行頭に `」、。ー` を置かない／行末に `「（` を置かない | 日本語組版の基本。PDF 帳票では必須 |
| 余白 | 4px グリッド、節間 24px | 詰めすぎず、間延びさせない |

### 6.5 情報密度

- 一覧の既定は 50 行（20 ではない）。密度切替を用意。
- 主要属性は常時表示。「展開して初めて見える」にしない。
- フィルタは既定で折り畳むが、選択条件はチップで常時表示。
- 一覧を大きなカードで作らない（縦方向を浪費する）。

### 6.6 国際化

| 項目 | 方針 |
|---|---|
| 既定 | `ja` |
| 対応 | `ja` / `zh-CN` / `en` |
| 実装 | i18next + interpolation（Phase 1）。ICU MessageFormat は Phase 2 |
| キー | `domain.component.element`（`impact.list.empty`） |
| 禁止 | 文字列連結で文を組む（語順が壊れる） |
| 複数形 | ICU `plural`（日本語は 1 種、英語は 2 種） |
| 検索正規化 | 全角/半角、ひらがな/カタカナ、旧字体を同一視（DB に正規化列） |
| ソート | 日本語ロケールの照合順序（`ja-x-icu`）。コードポイント順にしない |
| 数値・日付 | `Intl.NumberFormat` / `Intl.DateTimeFormat` |
| タイムゾーン | 保存は UTC、表示は `Asia/Tokyo` |

### 6.7 エラーメッセージの型

```text
【何が起きたか】+【なぜか】+【どうすればいいか】

× エラーが発生しました。
○ 設計書の解析に失敗しました。ファイルがパスワード保護されている可能性があります。
  保護を解除してから再アップロードしてください。

× 権限がありません。
○ この操作には「テスト承認」権限が必要です。プロジェクト管理者に依頼してください。
```

エラーコードは 2 行目の小字（例：`FORBIDDEN_PROJECT_SCOPE / trace: 4bf9...`）。**表示するのは `application/problem+json` の業務 `code` と `trace_id`**（`06-API.md` §1.1、`detail/04-api-contract.md` §0.1）。パーサー内部の `E-XLSX-xxx` は `detail.code` に小さく添えるだけにし、独自の `E-DOC-xxxx` 体系を作らない。

## 7. フロントエンド工程の制約

| 制約 | 内容 |
|---|---|
| ルートが状態 | Phase 1 は検索条件（`q` / `type`）と PDF 位置（`page` / `quote`）を URL に書く。一覧フィルタ・ソートの URL 化は Phase 2 |
| 型を重複定義しない | API 型は OpenAPI から生成 |
| コンポーネント層 | Phase 1 は `components/`（共通 UI）→ `pages/`（編成）。`features/` 分割は Phase 2 |
| グラフの隔離 | Cytoscape と React Flow を各々ラップし、状態を共有しない |
| 性能予算 | 初期 JS < 300KB（gzip）。グラフ画面は別 chunk |
| エラー境界 | feature ごとの ErrorBoundary は Phase 2。Phase 1 はページ単位の `ErrorNotice` |
| テスト | 重要操作は Playwright（基盤自身の E2E）。部品は Testing Library |
