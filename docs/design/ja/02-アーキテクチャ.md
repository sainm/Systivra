境界についての 3 原則：

1. **被テストシステムの実行環境は保持しない**。保持するのは接続設定のみ（A-06）。
2. **AI Provider は任意の外部依存**。停止しても、知識構築・コード解析・グラフ構築・影響計算・テスト資産管理は動作する（P6）。
3. **MCP は境界プロトコルであり、内部呼び出し方式ではない**。内部は必ず Capability を通す（§3）。

### 2.1 Capability 層を Engine 層から分ける理由

Engine は「どう計算するか」、Capability は「誰が、どのコストで、どの契約で計算してよいか」である。混ぜると：

- Agent が Engine を直接掴み、権限を閉じられない（プロンプト注入で越権）。
- MCP Tool が Engine メソッドに直結し、Provider 差し替えで Tool の意味が漂う。
- タイムアウト・クォータ・監査を一括でかけられない。

Capability は**唯一の実行入口**であり、MCP Server、Agent Tool、内部 UseCase のすべてがここを通る。違いは呼び出し元の身元と権限集合だけである。

## 3. モジュール境界

| モジュール | 所有するもの（唯一の書き手） | 依存してよい先 | 禁止 |
|---|---|---|---|

| `app` | ユースケースのトランザクション境界、冪等、Outbox | capability, store, domain, contracts, engine-rag（Phase 1 直接利用） | 解析・検索アルゴリズムの保有 |

> （検索融合・chunk・embedding）。Phase 2 で capability/runtime 経由に戻す。依存の境界を設計に戻す
> タイミングは `docs/phase1/handoff.md` の「置き換える場所」と同時に判断する。

**境界の判定**：1 つの変更で 2 モジュールの「所有物」を同時に触るなら、境界の引き方が間違っている。まず境界を直す。

> 表の名称は論理モジュールである。crate 名は `08-実装計画.md` §3 を正とする。`runtime::capability` は `runtime` crate 内、`providers::manager` は `providers` crate 内、`ontology` は `engine-graph` crate 内のモジュールを指す。`rag-engine` / `graph-engine` / `code-analysis` / `impact-engine` / `test-engineering` は、それぞれ crate `engine-rag` / `engine-graph` / `engine-code` / `engine-impact` / `engine-test` に対応する。`agent-runtime` と `workflow-engine` は `runtime` crate に含まれるが、層としては L5 に置く（crate の括りは層と一致しない）。

### 3.1 単一プロジェクト前提と KB の範囲

本製品は、特定の JavaWeb プロジェクト 1 件を対象とする。マルチテナント（複数プロジェクト / workspace 切替）は提供しない。

- `project` は 1 行だけを使い、**project 自体を知識ベース**とする。`knowledge_base` のような別エンティティは追加しない。
- 文書・コードは `project_id` に直接紐づける。既存の `corpus.document.project_id` / `code.repository.project_id` をそのまま使う。
- `project_id` と RLS は残す。テナント機能ではなく、**単一プロジェクトの防御線**として維持する。
- コード解析は Phase 4。Phase 1〜2 は文書のみを対象とする。
- 現行の 13 crate 構成と §3 のモジュール境界をそのまま使う。製品分離や共有カーネルの抽出は行わない。
- 将来マルチテナントが必要になった場合は、増分フラグではなく新しい ADR で扱う。現行の API / UI にプロジェクト切替を入れない。

#### 日本語プロジェクト固有の要件

| 領域 | 要件 | 正本 |
|---|---|---|
| 文字コード | Shift_JIS / CP932、外字、BOM、元バイト偏移。判定できない場合は推測せず未解析にする | `detail/06` §4.1、Phase 0 検証① |
| 日本語検索 | Lindera(IPADIC) + tsvector、unigram / bigram、pg_bigm、全半角・旧字体の正規化、クエリルーティング | `reference/japanese-search.md`、ADR-007 |
| 設計書 | Excel 中心。結合セル・図形アンカー・12 行ブロック・親子 chunk。PDF / DOCX / PPTX も対象 | `detail/01`、ADR-011 |
| コード | Java / JSP / XML / SQL。JSP は等長マスク + scriptlet 合成。日本語識別子を保持 | `detail/06` |
| 証拠 | 原文バイト位置、`quote` の部分文字列検証、PDF ハイライト | `04-コアエンジン.md`、`detail/04` |

#### バージョン管理（必須）

KB は次の 3 層を版管理する。検索・証拠・影響分析は、常に「どの版か」を持つ。

| 層 | 管理単位 | 操作 | 段階 |
|---|---|---|---|
| 原本 | `document_revision` / `code.revision`。content hash、CURRENT / SUPERSEDED、parser / analyzer 版を固定 | 履歴、現行切替、版指定検索、diff | K1 / K3 |
| 索引 | `index_build` + `embedding_model` | 索引版の指定、モデル切替、再構築 | K2 |
| KB スナップショット | 名前付きの版集合（document / code の revision を固定） | as-of 検索、release 比較、横断 diff | K4 |

- 証拠は `evidence.revision_id`、Fact は `revision_id` + `superseded_by` で版に固定する（既存設計）。
- KB スナップショットは現行 DDL に無い。K4 の着手前に `corpus.kb_snapshot` + manifest の DDL を追加する。
- 版を指定しない検索は「現在（CURRENT / is_current）」を既定とする。履歴検索は明示指定に限る。

段階分割は `08-実装計画.md` §3.2 を正とする。

### 3.2 知識管理と影響分析の境界

同一プロジェクト内で、**知識管理（KB）**と**影響分析（Impact）**を論理的に分ける。同じ DB を使うが、書き込み所有権は共有しない。

#### 能力の所有

| 能力 | KB | Impact | 共通 |
|---|---|---|---|
| 取込・解析・chunk・embedding・索引 | ● | — | — |
| 検索・証拠・原文定位 | ● | ○ 呼び出す | — |
| 文書 / コード版・索引版・KB snapshot | ● | ○ 参照 | — |
| 本体 / グラフ / 深いコード解析 / Fact / 影響計算 / テスト派生 | — | ● | — |
| 認証・ロール・監査・ジョブ・オブジェクトストレージ | — | — | ● |
| UI シェル・ログイン・ファイルプレビュー・証拠ドロワー | — | — | ● |

● = 唯一の書き手、○ = 読み取り / 呼び出しのみ。

#### データ所有

| データ | 書き手 | 読み手 |
|---|---|---|
| `core.*` / `ops.*` | 共通 | 両方 |
| `corpus.*` | KB | Impact は API / 読み取りビュー経由 |
| `code.repository` / `revision` / `source_file` / `symbol` | KB | Impact は読み取りのみ |
| `code.analysis_run` / `fact` | Impact | KB は参照のみ |
| `graph_meta.*` / `test.*` / `ai.*` | Impact | KB は参照しない |

- Impact は原本・chunk・evidence を複製しない。`document_revision_id` / `code_revision_id` / `index_build_id` / `kb_snapshot_id` だけを保持する。
- Impact が深いコード解析で原ファイルを必要とする場合は、KB の content API か共有オブジェクトストレージの読み取り経由で取得する。

#### 契約

1. **バージョン参照**：`document_revision_id` / `code_revision_id` / `index_build_id` / `kb_snapshot_id` が両システム間の唯一の内容識別子。
2. **内容 API**：revision 取得、原本取得、chunk 取得、evidence 取得、検索。Impact は KB の表を直接読まない（同一 DB でも読み取りビューに限る）。
3. **イベント**：`revision.ready` / `index.ready` / `revision.superseded` / `revision.deleted` / `snapshot.created`。Impact はこれで再計算を起動する。
4. **分析結果 API**：KB が影響表示を必要とする場合だけ Impact の読み取り API を呼ぶ。KB は影響を計算しない。

#### 配置

- **既定**：1 つのバックエンド内容コア + 2 つのフロント（KB / Impact）。認証・ジョブ・監査・ストレージ・UI kit を共有する。
- **独立配置が必要な場合**：KB を内容サービス、Impact を分析サービスとして API / イベントで接続する。同一 DB なら Impact に読み取り専用ロール / ビューを渡し、`corpus.*` と `code` 内容表への書き込みを禁止する。
- どちらの場合もマイクロサービス化はしない（ADR-001）。「2 システム」は論理境界であり、2 つの完全なスタックを作らない。

#### 禁止

- 2 本目の取込 / 解析 / chunk / embedding パイプライン。
- 原本 / chunk / evidence の複製。
- 2 つ目の文書 / コード版テーブル。
- 検索の再実装。Impact は KB search を呼ぶ。
- ログイン / 監査 / ジョブ / ストレージの再実装。

## 4. データの正本性と整合性

ここが最も事故りやすい。Prompt の「すべてを Neo4j に保存するな」に対する実装可能な答えを与える。

### 4.1 正本マトリクス

| データ | 正本 | 派生 / キャッシュ | 再構築方法 | 消失時の影響 |
|---|---|---|---|---|
| プロジェクト、ユーザー、権限 | PostgreSQL | — | バックアップ | 重大 |
| 文書メタデータ、改版 | PostgreSQL | — | バックアップ | 重大 |
| 原本バイト列 | Object Storage | ローカルキャッシュ | 提供元から再取込 | 中（再取込可） |
| 解析木 / doc_node | PostgreSQL | — | 再解析（結果が変わり得るため parser 版を固定） | 中 |
| Chunk テキスト | PostgreSQL | — | doc_node から再構築 | 中 |
| Embedding | PostgreSQL (pgvector) | — | 再 embed（同一モデル版が必要） | 低（再構築可） |
| Analysis Fact | PostgreSQL（**追記のみ**） | — | 再分析（同一 analyzer 版が必要） | 高（履歴が再現不能） |
| グラフ実体・関係 | **PostgreSQL** | Neo4j | Fact + entity から全件再投影 | 低（再構築可） |
| テスト資産・実行結果 | PostgreSQL | — | バックアップ | 重大 |
| スクリーンショット / trace | Object Storage | — | 再構築不能 | 中 |
| 監査ログ | PostgreSQL（追記のみ） | — | バックアップ | 重大（コンプライアンス） |

> **中核判断（ADR-002）**：Neo4j は「グラフにしか存在しないデータ」を持たない。すべての実体・関係・属性は PG に対応する行がある。Neo4j は検索加速と走査エンジンであり、削除して再構築できる。

### 4.2 Neo4j を正本にしない理由

1. **Provider 差し替え性**。Neo4j が唯一の事実源なら、「別のグラフ DB に替える」ことはデータ移行とリスクを意味し、Provider 抽象は嘘になる。
2. **トランザクション整合性**。テスト資産・承認・監査は関係変更と同一トランザクションでなければならない。PG/Neo4j 間の分散トランザクションは、「PG 単一トランザクション + 非同期投影」より高コスト。
3. **ライセンスと配置**（F-02）。Community は GPLv3。製品の一部として組み込めない。差し替え可能・不在可能（lite モード）であることが商業上の必要条件。
4. **証拠モデル**。関係は `revision / resolution / evidence` を持つ。これは関係構造であり、プロパティグラフに押し込むと「辺に JSON の塊」ができ、検索が難しくなる。

### 4.3 同期：Outbox + 冪等投影

```text
[トランザクション内]
  INSERT/UPDATE entity
  INSERT/UPDATE relationship
  INSERT outbox_event(event_id, aggregate, seq, type, payload, occurred_at)
COMMIT

[投影 worker]
  SELECT ... FROM outbox_event
   WHERE published_at IS NULL
   ORDER BY seq
  FOR UPDATE SKIP LOCKED LIMIT 5000
  → event / 関係型ごとに 1,000 件を UNWIND（条件付き書き込み）
  → published_at を更新
```

| 問題 | 対策 |
|---|---|
| 順序逆転 | `entity_id` ごとに `projection_seq` を保持。`WHERE e.projection_seq < $seq` で古いイベントを捨てる |
| 重複送信 | `event_id` 一意制約 + `MERGE`。投影側に `last_event_id` |
| 部分失敗 | 1 件の失敗でバッチを止めない。`outbox_dead_letter` に退避し、閾値超で警報 |
| 削除伝播 | 物理削除しない。`deleted_at` + `ProjectionTombstone`。グラフ側は `DETACH DELETE` を分割実行 |
| 全件再構築 | `POST /api/v1/projects/{pid}/graph/rebuild` で PG live 行を keyset 走査し、`UNWIND` 再投影。現実装は in-place、影ラベル切替は未実装 |
| 漂流検出 | 毎日 1,000 実体を抽出し、PG と Neo4j の次数・属性ハッシュを比較。差分率 0.1% 超で警報 |

### 4.4 削除と改版

文書更新は「上書き」ではなく `document_revision` の追加。旧 revision の chunk は残すが `superseded_at` を付ける。検索は既定で `is_current = true` のみ、履歴検索は revision を明示する。

```text
1. document_revision.status = 'superseded'      (PG, トランザクション内)
2. outbox: DocumentRevisionSuperseded
3. 投影：関連 entity/relationship の revision を失効
4. RAG：chunk.superseded_at = now()。現行索引から論理除外（ベクトルは即削除しない）
5. 非同期 GC：N 日超の superseded chunk を物理削除 + ベクトル削除
```

手順 4 の「即時削除しない」は意図的である。削除すると実行中の影響分析が中途半端な証拠を掴む。`is_current` で読み取り一貫性を保つ。

## 5. データフロー

### F1 知識構築（文書 → 検索可能な証拠）

```text
アップロード / 同期
  → content_hash 計算（重複排除）
  → document_revision 作成（source_revision / acquired_at を固定）
  → parse job を enqueue
      → ParserProvider 振り分け：
          XLSX          → 自作 Rust パーサー（calamine + OOXML）
          PDF/DOCX/PPTX → docling-serve（既製コンテナ）
          MD/TXT/CSV    → ネイティブ
          HTML          → ネイティブ（scraper + 構造抽出）
      → DocNode 木を生成（locator 付き）
  → 構造分類（doc_type / business_domain / screen 紐付け）
  → 意味チャンク（構造認識。04.1 参照）
  → メタデータ抽出 + エンティティリンク候補
  → Embedding（バッチ、中断可能、チェックポイント再開）
  → pgvector + tsvector へ書き込み
  → outbox: ChunkIndexed → グラフ投影（Document / Section のみ。chunk は投影しない）
```

各段に `parse_run` を持ち、任意の段から再実行できる。最初からやり直さない。

### F2 関係構築（コード → Fact → グラフ）

```text
[1] 同期
    Repository 同期（Git/Dir/Snapshot）→ revision（commit sha / tree digest）
    ※ SVN は未導入（将来拡張）
    → 変更検出（added/modified/deleted/moved）

[2] 前処理
    ファイル分類・言語判定・文字コード判定 → UTF-8 内部表現

[3] 構文・関係抽出
    Tree-sitter tags → シンボル、import、注釈、文字列リテラル
    プロジェクト内シンボル索引 → 同一 revision の class / method / field を照合し、
                                一意な関係は RESOLVED、複数候補は INFERRED
    Framework Adapter → Action マッピング、Dicon DI、JSP taglib、SQL 紐付け
    Config Analyzer → XML/YAML/Properties/CSV

[4] Fact 統合・永続化・投影
    Fact へ正規化 → 競合検出 → supersede → outbox: FactAccepted → グラフ投影
```

### F3 影響分析（変更 → 影響レポート）

```text
入力：change_set（diff / 手動指定 / 要件変更）
  → ① シード解決：ファイル + 行 → 所属シンボル（tree-sitter）→ entity_id
  → ② 変更分類：コード / 設定 / DB / 文書 / API
  → ③ 逆方向走査（呼び出し元、実装元、参照元）  ┐
  → ④ 共有リソース閉包（表、外部 API、ファイル）  ├─ 決定論（impact-engine）
  → ⑤ 順方向走査（DB 書き込み、外部呼び出し）    ┘
  → ⑥ 文書証拠検索（実体名 + 業務ルール語 → RAG、フィルタ付き）
  → ⑦ テスト資産照合（トレーサビリティ：entity → test_case）
  → ⑧ リスク評点（決定論。04.5 参照）
  → ⑨ AI 補足：漏れ仮説、業務説明（INFERRED。主表には入れない）
  → ⑩ ImpactReport + グラフ + 証拠パッケージ
```

### F4 テスト閉ループ

```text
ImpactItem / BusinessRule
  → Scenario 派生（業務フロー / 異常 / 境界 / 状態遷移 / 同時実行）
  → Case 派生（手順 + 入力 + 期待値。evidence を紐付け）
  → Data 派生（同値類 + 境界。ValidationRule 由来）
  → 人手レビュー（Draft → Approved）
  → TestRunnerProvider（Playwright）実行
  → 結果収集（スクリーンショット / trace / log / アサーション）
  → Coverage 再計算（4 次元）
  → 失敗 → Defect（evidence と impact を紐付け）
```

### F5 AI 呼び出し（統制下）

```text
AgentRun 開始（予算：tokens / tool_calls / wall_time / cost）
  → Agent が Capability を呼ぶ（Tool 名ではなく能力名）
  → Capability Gateway：
       1. 入力 JSON Schema 検証
       2. agent ホワイトリスト ∩ ユーザー権限 ∩ プロジェクト範囲
       3. trace_id / project_id を注入（Agent は上書き不可）
       4. 実行（タイムアウト / キャンセルトークン）
       5. 出力 Schema 検証
       6. untrusted=true を付与（文書・外部 MCP 由来）
       7. 監査（who / what / why / cost / duration）
  → 結果は Agent に「データ」として返す（命令として扱わせない）
```

## 6. 実行時アーキテクチャ

### 6.1 プロセス構成

| プロセス | 言語 | 役割 | スケール | 状態 |
|---|---|---|---|---|
| `sep-api` | Rust | HTTP/SSE、認証、ユースケース | 水平スケール（ステートレス） | ローカル状態なし |
| `sep-worker` | Rust | 解析編成、投影、影響計算、テスト編成 | 水平スケール（キューで分割） | job 表で調整 |
| `docling-serve` | Python | Docling 解析（既製コンテナ。自作コードなし） | 水平スケール（CPU/GPU 集約） | ステートレス |
| `test-runner` | Node | Playwright 実行 | 水平スケール（ブラウザ単位） | 一時 workspace |

**docling-serve を別プロセスにする理由**：

- 依存衝突：Docling は特定の PyTorch/Python に依存し、Rust の解析プロセスと実行環境が異なる。
- 障害分離：壊れた Excel 1 件で API を落としてはいけない。
- 資源特性：Docling はメモリと CPU を消費し、API は接続数を管理する。

ただし**業務状態は持たない**。「入力バイト → 構造化結果」のみ。状態はすべて Rust 側に戻す。

### 6.2 同時実行と背圧

```text
API リクエスト → enqueue（job 表）→ 202 + job_id を即返却
                │
                ├─ キューは (project_id, priority) で分割
                ├─ 種別ごとに同時実行上限（Excel 解析 8〜16 / 投影 8 / 影響 4 / 実行 2）
                ├─ 全体制限：単一プロジェクトの同時ジョブ数に上限
                └─ 背圧：キュー深さが閾値超なら PENDING のまま推定待ち時間を提示
```

ジョブ状態（厳密）：

```text
PENDING → QUEUED → RUNNING → SUCCEEDED
                    │  ├──→ FAILED → (retry) → QUEUED
                    │  ├──→ CANCELLED
                    │  └──→ WAITING_APPROVAL → RUNNING
                    └──→ TIMEOUT → FAILED
```

冪等性：`idempotency_key = hash(project_id, operation, input_digest, revision)`。再送信は同一 `job_id` を返し、実行しない。

チェックポイント：5 分超のジョブは N 単位ごとに `job_checkpoint`（処理済みファイル、カーソル）を書く。プロセスクラッシュ後はチェックポイントから再開する。

### 6.3 キャンセル

`CancellationToken` を Capability → Engine → Provider まで通す。Provider はキャンセルに応答する（HTTP abort、子プロセス kill group）。**「API はキャンセル成功と言ったのに worker が動いている」状態を許さない**。画面では成功、裏では半端なデータが書かれる事故につながる。

```yaml
services:
  api:            sep/api:0.1        # :8080

  minio:          minio/minio
  otel-collector: otel/opentelemetry-collector-contrib
volumes:
  pgdata, neo4jdata, miniodata, workspace
```

### 7.2 3 つの提供形

| 形 | 構成 | データ分離 | 用途 | 差分 |
|---|---|---|---|---|
| **Local / Dev** | 全コンテナ + `lite` profile | 単一 DB | 開発、デモ | Graph は `PgGraphProvider`（再帰 CTE）で代替可。AI は Ollama か停止 |
| **オンプレ（既定）** | 全コンテナ、顧客閉域網 | 単一 DB 内で schema / 行分離 | 日本企業 | オフラインイメージ。AI 任意。監査ログを SIEM へ |
| **SaaS（将来）** | テナントごとに schema または DB | 物理分離（推奨） | 複数顧客 | SSO、クォータ、テナント横断運用。Phase 8 で検討 |

### 7.3 lite profile の意味

「機能を削った版」ではなく**検証可能性の担保**である。Neo4j を外しても中核閉ループが成立することを示す。できなければ、グラフ能力が過結合している証拠になる。

`PgGraphProvider` の能力宣言（04.10）は「1〜3 ホップの隣接と経路は可、大規模サブグラフ出力とグラフアルゴリズムは不可」。能力マトリクスでは `PARTIAL` と表示し、UI で明示する。

### 7.4 資源の初期値（単一プロジェクト、A-02 規模）

| サービス | 台数 | CPU | メモリ | ディスク |
|---|---|---|---|---|
| xlsx 解析ワーカー（`sep-worker` 解析プール） | 16 | 4 | 8 GB | 50 GB |
| postgres | 1 | 16 | 64 GB | 2 TB NVMe |
| neo4j | 1 | 8 | 64 GB | 500 GB |
| minio | 2 | 4 | 8 GB | 2 TB |

> 全サービスと根拠は `reference/scale-model.md` §7 を正とする。旧想定（20 万 chunk、4 CPU / 16 GB）の値は使わない。Phase 2 と Phase 4 で実測し、更新する。

## 8. 想定される失敗モード

| 失敗 | 契機 | 症状 | 予防 |
|---|---|---|---|
| 投影漂流 | Outbox 消費失敗を検知できない | グラフに辺が欠け、影響分析が黙って漏れる | 日次漂流検出 + 「グラフ完全性」をホームに表示 |
| 証拠の宙吊り | 文書改版後も chunk が有効 | 証拠を開くと空白・位置ずれ | revision 固定 + stale 表示 + サンプル検証 |
| 解析雪崩 | 巨大 XLSX が docling-serve を占有 | 他案件がタイムアウト | サイズ/ページ上限 + 専用キュー + サーキットブレーカ |
| トランザクション越境 | Capability 内で tx を開始し、呼び出し側も開始 | デッドロック、部分コミット | tx は app 層のみ。engine は `&mut Tx` を受けるだけ |
| 冪等性の破綻 | 再試行時の input_digest に日時を含める | 資産が二重生成 | 冪等キーは内容のみから作る |
| AI の越権 | Agent が project_id を引数で渡す | 他プロジェクトを読む | project_id はゲートウェイが注入。Agent からは不可視 |
