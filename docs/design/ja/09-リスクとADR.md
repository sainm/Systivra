# 第 9 部：リスクと意思決定

## 1. リスク登録簿

評価は「発生可能性 / 影響」の 2 軸。RPN は影響 × 可能性の目安で、順序付けに使う（厳密な計算ではない）。

> **並び順について**：本表は「日本語コーパス / 規模 / グラフ / AI / 運用」の**主題別グループ**で並べており、ID の番号順ではない。R-22〜R-26 は 2026-11-05 の実規模ヒアリング後に追加したため、技術リスク群の末尾に置いてある。ID は不変の参照キーとして扱い、挿入に伴う再採番はしない。

## 2. アーキテクチャ決定記録（ADR）

### ADR-001：モジュラーモノリス + 独立 Worker（マイクロサービスにしない）

- **状態**：承認済み
- **背景**：10 のエンジン、4 言語の実行環境。マイクロサービスは「分離」に見えるが、分散 tx、サービス横断追跡、配置編成を持ち込む。
- **決定**：単一 Rust プロセスが API と中核エンジンを担う。Python/Java/Node は**ステートレスな形式変換 Worker** とし、HTTP/NDJSON で通信。業務状態を持たない。
- **結果**：単一 tx 境界、デバッグ容易、compose 1 つで起動。一方で単一障害点になるため、モジュール境界の規律が必要。分割の契機は「50 並行ジョブを捌けない」「チーム 15 名超」。

### ADR-002：PostgreSQL を唯一の正本、Neo4j を再構築可能な投影

- **状態**：承認済み（2026-11-05 確定）
- **背景**：Prompt の「すべてを Neo4j に置くな」と Provider 差し替え要求。
- **決定**：実体・関係・属性はまず PG（`graph_meta`）に書く。Outbox 経由で Neo4j に投影。Neo4j は削除して再構築できる。
- **結果**：差し替え可能、tx 整合、ライセンス制御、lite モード。代償は二重保存、秒単位の投影遅延、漂流検出の運用。**「Neo4j にしか書かない」コードパスを禁止**。

### ADR-003：RAG は自作。Provider には「検索実行」だけを委ねる

- **状態**：承認済み
- **背景**：RAGFlow 等を中核にすると構造意味と証拠契約を失う。完全自作はベクトル検索の再実装になる。
- **決定**：取込・構造モデル・チャンク・メタデータ・証拠・文脈組立は自作。`RagProvider` は索引書き込みと検索実行のみ。
- **結果**：分割戦略を制御でき、証拠契約が統一され、Provider 交換で業務が変わらない。chunk ライフサイクルと索引版の保守は自前。

### ADR-004：Analysis Fact は追記のみ、解決状態は 5 種

- **状態**：承認済み
- **背景**：解析結果はコードとアナライザー版で変わる。上書きすると履歴が消え、再現できない。
- **決定**：`code.fact` は追記のみ。新解析は `superseded_by` で旧版を失効。各 Fact に `resolution / confidence / engine_version / evidence`。
- **結果**：再現・比較・監査が可能。保存量が増え、照会に `valid_to IS NULL` が必須（repository で強制）。

### ADR-005：Capability を唯一の実行入口とする

- **状態**：承認済み
- **背景**：Agent、MCP、フロント、内部ユースケースがそれぞれエンジンを呼ぶと、権限と監査を閉じられない。
- **決定**：すべて `Capability Gateway` を通す。Schema 検証、権限積集合、`project_id` 注入、予算、タイムアウト、監査、出力検証を一箇所で行う。
- **結果**：越権と注入の防衛線が集中し、MCP/Agent/フロントが同じ意味を共有。間接層と Schema 保守のコスト。

### ADR-006：AI Provider は二実装。Copilot に固定しない

- **状態**：承認済み
- **背景**：Copilot SDK は GA で Rust SDK もあるが、実行時に Copilot CLI サイドカーを要し、GitHub 購読または BYOK が前提。閉域網では強制できない。
- **決定**：`OpenAiCompatProvider` を既定（DeepSeek / vLLM / Ollama / Azure 互換）。`CopilotRuntimeProvider` は agent loop が必要な場合の任意実装。
- **結果**：オフライン可、単一ベンダー非依存、コスト制御。二実装の ToolCall 意味を統一する必要。**Copilot 内部 API の逆プロキシは禁止**。

### ADR-007：日本語検索は「階層型語彙 + クエリルーティング」

- **状態**：承認済み（2026-11-05）
- **背景**：PG の既定全文検索は日本語非対応。pg_bigm / PGroonga は拡張が必要。さらに現場には自然言語検索と部分一致・識別子検索が混在し、単一方式では 半分が成立しない。
- **決定**：
  - **L1 常時**：Lindera(IPADIC) → `tokenized` → `tsvector('simple')` + GIN。拡張不要。
  - **L2 条件付き**：`pg_bigm` があれば `chunk.text` に GIN（`gin_bigm_ops`）。部分一致と未登録語。
  - **L3 再利用**：顧客既存の PGroonga のみ接続。既定依存にしない。
  - **ルーティング**：識別子 / 引用句 / 4 文字以下の短入力は BIGRAM。それ以外は TOKENIZED。両方可なら並行し RRF 融合。`lexical_mode` を返す。
- **結果**：拡張なしでも動き、あれば体験が向上。二索引の書き込みコスト、辞書版と索引の固定、ルーティング調整の継続が必要。
- **詳細**：`reference/japanese-search.md`

### ADR-008：影響分析は決定論的走査。AI は叙述と仮説のみ

- **状態**：承認済み
- **背景**：AI に影響範囲を判断させると再現不能・監査不能・漏れやすい。
- **決定**：影響項目は Rust のグラフ走査 + 規則評価で生成し主表に書く。AI は `narrative` と `hypotheses`（`INFERRED`、既定折り畳み、人手採用）のみ。
- **結果**：再現・説明・比較が可能。走査と hub 処理の設計が必要。長尾の漏れは「未解析一覧」で補う。

### ADR-009：テスト実行は JSON ステップ DSL（コード生成にしない）

- **状態**：承認済み
- **背景**：`.spec.ts` の生成は柔軟だが、任意コード実行の sandbox が必要で検証しにくく、版更新で壊れる。
- **決定**：JSON ステップを汎用 Runner が解釈実行。`custom_step` は拡張点として用意し、既定は無効。
- **結果**：安全・検証可能・版管理可能・Runner 間で可搬。表現力に制約（複雑な操作はステップ型を追加）。

### ADR-010：Workflow は自作、YAML を唯一の意味ソース

- **状態**：承認済み
- **背景**：Dify は組込み可能なエンジンではなく完全アプリ。Temporal は運用が重くプログラミングモデルも異なる。
- **決定**：Rust ステートマシン + YAML。キャンバスは YAML の投影で、レイアウトは `x-ui-layout`。編集は構造化 patch。
- **結果**：Capability / 承認 / 監査と深く統合でき、配置も単純。長時間タイマーや複雑な補償は自前。`WorkflowRuntime` trait は保持。

### ADR-011：XLSX は自作解析。Docling を使わない

- **状態**：承認済み
- **背景**：日本の設計書は「セルで組んだキャンバス」。Docling の XLSX 出力は結合意味、図形、数式/キャッシュ値の区別を失う。
- **決定**：`calamine` + OOXML 直接解析（`xl/worksheets`、`xl/drawings`、`xl/sharedStrings`）。Docling は PDF/DOCX/PPTX のみ。
- **結果**：セル単位の忠実度、`Sheet!Range` の証拠位置、Python 非依存。自作工数と、グラフ/複雑スタイル非対応（明示）が代償。

### ADR-012：フロントの2グラフライブラリは用途分離

- **状態**：承認済み
- **背景**：関係図とフロー図はデータモデル・操作・性能特性が異なる。
- **決定**：Cytoscape.js は関係/依存/影響図。React Flow は Workflow/Agent/承認フロー。相互に代替しない。
- **結果**：各々の長所を活かせ、大規模図の性能を制御できる。依存と操作規則が二系統になる。

### ADR-013：Neo4j は 5.26 LTS、クエリは Cypher 5 サブセット

- **状態**：承認済み（2026-11-05）
- **背景**：**Neo4j に「2026.x LTS」は存在しない**。2025 年以降はカレンダーバージョンで、各月版は翌月版までしか hotfix されない。唯一の LTS は 5.26（2028-06-06 まで）。4.4 LTS は 2025-11-30 に終了。
- **決定**：
  1. 基盤は **5.26.32**。独立サービスとして配布（組込み・リンクなし）。
  2. 生成する Cypher は **Cypher 5 の文法サブセット**。Cypher 25 専用構文と `CYPHER 25` 接頭指定を使わない。
  3. 2026.x は「顧客が既に持つ場合の互換対象」。CI ゲートは 5.26、2026.x は互換検証のみ。
  4. 2027 H1 に次の LTS を評価。無ければ 5.26 のサポート期限内（2028-06）で移行計画を確定。
- **結果**：顧客に毎月の DB 更新を強いない。Cypher 5 サブセットは 2026.x でも動く。Cypher 25 の新機能は使えない。

### ADR-014：単独問合せは「別エンジン」ではなく ImpactReport のプロファイル

- **状態**：承認済み（2026-11-05）
- **背景**：ユーザーは「XX を変更したら何が起きるか」を、影響分析の主ワークベンチを開かずに単独で問いたい。答えは **概要 / 影響画面 / 影響文書 / 影響コード / どうテストするか** の 5 つに固定されている。
- **決定**：
  1. Q-01（変更影響問合せ）は、`04-コアエンジン.md` §4.5 の ImpactEngine に **`profile = CHANGE_INQUIRY`** を渡した結果を 4 分類へ投影したものとする。新しい走査・評点ロジックを作らない。
  2. 応答は **`impact_id` を返す**。A-04 / A-05 と同じ ImpactReport を指し、掘り下げても数字が変わらない。
  3. 自然言語は**シード解決だけ**に使う。結論・リスク・証拠を AI に書かせない。曖昧なら `NEEDS_CLARIFICATION` で止める。
  4. テストは**提案まで**。計画に渡すが実行しない（D-04 と整合）。
- **結果**：Q-01 と A-04 で件数・順序・リスクが一致する。プロファイル分岐だけなので実装は小さい。代わりに「Q-01 だけの特別な見解」は出せない（それが正しい）。
- **却下案**：Q-01 専用の軽量エンジン（速いが A-04 と答えが食い違う）、AI に 5 ブロックを書かせる（根拠のない断定と証拠の捏造を招く）。
