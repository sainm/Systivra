# 第一部分：产品定位

## 1. 一句话定位

> **把「设计书、代码、数据库、测试」放在同一张可追溯的证据图上，让每一次改修的影响范围可以被计算、被验证、被审计。**

Systivra 是一个面向企业遗留系统维护场景的**软件工程智能分析与测试自动化平台**。它不是文档问答机器人，也不是代码扫描器，而是一套「**工程事实 + 证据 + 关系 + 闭环**」的基础设施。

三个限定词决定了它和通用工具的分野：

| 限定 | 含义 | 反面 |
|---|---|---|
| 可追溯 | 每条结论都能回指到「哪份文档的哪一页 / 哪个 Excel 单元格 / 哪个文件的哪一行」 | 只给一段没有出处的自然语言 |
| 可计算 | 影响范围、覆盖状态由确定性算法算出，AI 只负责解释与补充假设 | 让 AI 凭印象列出「可能影响」 |
| 可闭环 | 测试资产由影响分析派生，覆盖状态由**实际执行结果**判定 | 「生成了用例」就宣称「已覆盖」 |

## 2. 使用者

平台不是给单一角色用的。四类角色的诉求差异极大，这直接决定了 UI 必须有三套信息密度不同的视图（见 `07-ui.md`）。

| 角色 | 典型画像 | 真实诉求 | 平台给出的东西 | 主要入口 |
|---|---|---|---|---|
| **项目经理 / 保守运用负责人**（橋本、45 岁） | 手上同时管 3 个改修案件，客户每周问「这次改修要多久、会不会影响别的功能」 | 影响范围与工数依据；出事时能说清「我们查过了」 | 影响分析报告（分层 + 证据 + 风险）；回归测试范围 | 项目总览 / 影响分析 / 报告导出 |
| **上游 SE / 业务分析师**（田中、38 岁） | 写基本设计书与详细式样书，熟悉业务但读不动代码 | 这条业务规则到底写在哪儿、代码有没有实现 | 业务规则 ↔ 设计书 ↔ 实现代码的追踪矩阵 | 文档检索 / 追踪矩阵 / 规则清单 |
| **开发 / 维护工程师**（佐藤、32 岁） | 接手 15 年前的系统，改动前先花两天读代码 | 我改这个方法，谁在调我；这张表还有谁在写 | 调用链、反向依赖、共享资源消费方 | 代码分析 / 依赖图 / 影响图 |
| **测试负责人 / QA**（鈴木、41 岁） | 1000 多条校验规则，靠人肉记 Excel；回归靠经验挑 | 该测什么、测够了没有、能不能证明 | 规则清单、测试数据生成、执行结果、覆盖矩阵 | 测试计划 / 覆盖矩阵 / 执行看板 |
| **架构 / 质量管理者**（山本、50 岁） | 要面对审计与客户质量审查 | 这套工具自己的结论可信吗 | 解析状态分布、置信度、Provider 能力矩阵、审计日志 | 平台管理 / 审计 / 分析历史 |

> 设计含义：**同一份数据，四种叙事**。项目经理看到的是「影响 7 个画面、3 条业务规则、风险中」，工程师看到的是「14 条调用边、2 处反射调用未解析」，测试看到的是「新增 23 个 case、其中 9 个已执行通过」。这不是四套数据，是同一组 `impact_item` 的四个投影。

## 3. 核心场景

### S1 改修影响调查（主场景）

客户提出「住所校验要改成只允许全角汉字与数字，长度从 20 改到 30」。工程师只改了一个 `Validator` 方法和一个 JSP 的 `maxlength`。

平台需要回答：

1. 这次变更实际改了哪些文件、哪些方法（确定性：diff → 符号定位）。
2. 谁调用了这个校验方法（反向 `CALLS`，含间接调用）。
3. 哪些画面会走到这条校验（`Screen → Action → Service → Validator` 路径）。
4. 哪些业务规则文档描述了这个校验（RAG + 实体链接，带页码）。
5. 数据库字段长度是否匹配（`Column.length=20`，确定性冲突检测）。
6. 有没有别的地方也在写这张表（共享资源闭包）。
7. 哪些既有测试用例覆盖了这些画面（追踪矩阵）。
8. 哪些是**无法确定**的（反射、动态代理、字符串拼装的方法名）。
9. 风险等级与建议的回归范围。

产出：`ImpactReport`（结构化 JSON + 图 + Markdown/PDF），每个影响项带 `path`、`evidence`、`resolution`、`confidence`。

### S2 遗留系统结构理解（onboarding / 黑盒化解体）

新接手的系统没有架构文档。平台从代码与配置中重建：

- 画面清单（JSP + Action 映射 + `web.xml`/Dicon）
- 分层结构与实际调用关系（不是「理论上应该有」，而是「实际解析到的」）
- 数据访问全景（哪些 Service 读写哪些表）
- 死代码与孤儿画面（无入边的 Action）
- 未解析清单（明确告诉人「这些我看不懂」，而不是猜）

价值：把「两周读代码」压到「两小时看图 + 半天验证」。

### S3 设计书问答与证据追溯（保守运用 / 问询应答）

运营团队每天收到「这个项目为什么这么校验」「这个画面的项目定义在哪儿」的问题。平台给出**带定位的答案**：

- Excel 设计书精确到 `Sheet / 单元格区域`
- PDF 精确到 `页码 + 区块`
- Word 精确到 `章节`
- 代码精确到 `文件:行`

并且明确区分「文档这么写的」「代码这么实现的」「两者不一致（CONFLICT）」。

### S4 测试资产派生与回归闭环

从 S1 的影响项出发：

`ImpactItem → TestScenario（业务流/异常/边界）→ TestCase（可执行步骤）→ TestData（等价类+边界）→ Playwright 执行 → TestResult → Coverage`

关键约束：**Case 必须能执行**。不能执行的不叫 Case，叫「待补充的测试想法」，单独存 `test_idea`，不计入覆盖率。

### S5 校验规则清点（1000 条规则的现实）

从 Java / JSP / JavaScript 中抽取校验规则，形成 `ValidationRule` 目录：

| 字段 | 例 |
|---|---|
| rule_id | `RULE-USER-ADDR-001` |
| source | `UserEditAction.java:128` / `user_edit.jsp:74` |
| field | `住所` |
| type | `LENGTH` / `REQUIRED` / `PATTERN` / `RANGE` / `CROSS_FIELD` |
| condition | `全角 && length <= 20` |
| valid / invalid / boundary | `東京都…` / `ABC` / `20 文字ちょうど` |
| evidence | 详细设计书 `画面項目定義!C12` |

1000 条规则对应约 3000~5000 条测试数据。手工维护不可能，必须由规则自动生成并允许人工修订（修订留痕）。

## 4. 主要业务闭环

```text
   要件・設計資料 ──┐
   ソースコード   ──┼─→ ① 知識構築 ──→ ② 関係構築 ──→ ③ 影響分析
   DB / 設定      ──┤   (RAG/Chunk)      (Graph/Fact)      (Impact)
   テスト資産     ──┘                                        │
          ↑                                                  ↓
          │                                          ④ テスト設計
          │                                        (Plan/Scenario/
          │                                         Case/Data)
          │                                                  │
          └──── ⑦ 学習・改善 ←── ⑥ 被覆判定 ←── ⑤ 実行・記録
                (Feedback)        (Coverage)      (Playwright)
```

七步中，**只有 ③ 和 ④ 允许 AI 深度参与**，其余五步都是确定性程序。这是平台可信度的来源，也是与「AI 测试生成器」的根本区别。

闭环的判定条件（Definition of Closed）：

> 一次变更，在没有任何人工补充说明的情况下，平台能输出「影响项 → 对应用例 → 执行结果 → 覆盖结论」的完整链条，且每个环节都有证据可查。任一环断裂，闭环不成立。

## 5. 与三类工具的区别

### 5.1 对比总表

| 维度 | 普通 RAG 系统 | 代码分析工具 | 测试管理工具 | **Systivra** |
|---|---|---|---|---|
| 基本单元 | Chunk（文本块） | 文件 / 符号 | 用例 / 缺陷 | **Entity + Fact + Evidence** |
| 结构保留 | 弱（切块即丢结构） | 强（AST/LST） | 无 | **强（文档树 + 代码符号 + 表格坐标）** |
| 关系表达 | 向量相似度 | 调用/继承 | 无 | **类型化关系图，带来源与解析状态** |
| 版本绑定 | 通常无 | 分支级 | 无 | **每个结论绑定 revision，可复现** |
| 结果可信度 | 不可度量 | 规则内确定 | 人工判定 | **RESOLVED / INFERRED / PARTIAL / UNRESOLVED / CONFLICT 五态** |
| 跨域追踪 | 无 | 无 | 弱（手工关联需求） | **文档↔代码↔DB↔测试 四向追踪** |
| 测试闭环 | 无 | 无 | 有资产无派生 | **影响项派生用例，执行结果反算覆盖** |
| 主要失败模式 | 答得像但找不到出处 | 图很漂亮但业务看不懂 | 用例写完就烂掉 | **解析不全 → 显式暴露，不假装完整** |

### 5.2 与 RAG 的区别：证据契约

普通 RAG 的输出是「一段话 + 几个文档名」。Systivra 的输出是 `Evidence` 结构：

```json
{
  "evidence_id": "EV-7f3a...",
  "source_type": "EXCEL_CELL_RANGE",
  "document_id": "DOC-0012",
  "revision_id": "REV-0007",
  "locator": { "sheet": "画面項目定義", "range": "C12:F12", "row": 12 },
  "quote": "住所：全角20文字以内。未入力時エラー",
  "chunk_id": "CH-9a1c...",
  "resolution": "RESOLVED",
  "confidence": 1.0
}
```

三条硬规则：

1. **无 locator 不入库**。解析不出来就标 `UNRESOLVED`，不允许生成「大概在第三章」。
2. **引用可跳转**。前端点击证据直接打开原文并高亮，不是弹一个文本片段。
3. **证据有版本**。文档改版后旧结论标记 `stale`，而不是静默失效。

### 5.3 与代码分析工具的区别：业务语义层

jQAssistant / Spoon / JavaParser 能告诉你 `A calls B`。它们不能告诉你：

- `B` 对应哪条业务规则
- 这条规则写在详细设计书的哪一页
- 哪个画面会触发它
- 改动它要跑哪些测试

Systivra 的代码分析产出不是「图」，而是**进入统一 Fact Model 的事实**，再与文档实体、测试资产在同一张图上对齐。代码分析只是四个事实来源之一。

同时要诚实：**代码分析永远不可能 100% 完整**。反射、动态代理、字符串拼装 SQL、JSP 自定义标签、JavaScript 动态行为，这些地方平台会明确标记 `INFERRED` 或 `UNRESOLVED`，并给出「为什么无法确定」。一个声称 100% 准确的调用图，比一个标注了 82% 覆盖率的调用图更危险。

### 5.4 与测试管理工具的区别：派生而非登记

Kiwi TCMS 这类工具的核心是「登记与执行」。Systivra 的核心是「**派生**」：

| | 测试管理工具 | Systivra |
|---|---|---|
| 用例来源 | 人写 | 从影响项 / 业务流 / 校验规则派生，人修订 |
| 与需求的关系 | 手工打标签 | 图上的一条边，带证据 |
| 覆盖率的含义 | 用例执行率 | **需求/规则/画面/影响项四维覆盖，且只认执行结果** |
| 变更后的动作 | 人工判断哪些用例失效 | 影响分析自动标记受影响的用例集 |
| 数据生成 | 手工填 | 从校验规则生成等价类/边界值，可追溯 |

## 6. 产品原则（可执行的版本）

不是口号，是评审时的判据。

| 原则 | 判据（评审时问这句话） |
|---|---|
| P1 确定性优先 | 这个结论如果是程序能算的，为什么交给 AI？ |
| P2 证据先行 | 这条结论点进去能看到原文吗？看不到就不能发布。 |
| P3 显式不确定 | 解析不了的地方，界面上有没有告诉用户「这里不可靠」？ |
| P4 版本可复现 | 三个月后拿同一个 revision 重跑，结果一致吗？ |
| P5 可替换 | 把 Neo4j 换成别的库，业务代码要改几行？（答案必须是 0） |
| P6 无 AI 可用 | 断掉所有 AI Provider，平台还能完成哪些事？（必须覆盖 ① ② ③ ⑤ ⑥） |
| P7 不假装完整 | 界面上「未解析」的数量是不是可见的？藏起来就是欺骗。 |

## 7. 非目标（Non-goals）

明确不做，避免范围蔓延：

1. **不做 IDE**。编辑器只用于查看与 diff 预览，不做代码补全。
2. **不做 CI/CD 平台**。只对接既有流水线，产出测试资产与结果。
3. **不做通用聊天机器人**。所有对话必须绑定项目上下文与能力白名单。
4. **首期不自动改代码**。只输出建议 patch，人工确认后由客户侧提交（见 A-07）。
5. **不做通用 BI**。图表只服务于工程分析，不做自由拖拽报表。
6. **不做代码质量评分**。静态扫描规则（复杂度、重复率）可以接入，但不做「分数」这种不可解释的指标。
7. **不做跨客户知识共享**。项目隔离是硬约束（A-10）。

## 8. 成功判据

Phase 结束时用这些指标判断「是否真的有用」，而不是「功能是否做完」。

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 影响调查耗时 | 从 2 人日降到 2 小时以内 | 真实改修案件的计时对比 |
| 影响项召回率 | ≥ 90%（人工基线对照） | 抽取 20 个真实变更，人工列出影响项做金标 |
| 影响项精确率 | ≥ 70%（允许有依据的过度包含） | 同上；过度包含必须标注理由 |
| 证据可定位率 | ≥ 95% 的结论可跳转到原文 | 抽样 200 条 evidence 人工核验 |
| 未解析显式率 | 100%（不允许静默丢弃） | 检查 `UNRESOLVED` 是否有 UI 呈现 |
| 测试资产可用率 | ≥ 60% 派生用例可直接执行 | 首次执行通过率 |
| 回归覆盖判定准确率 | ≥ 85% | 与实际缺陷漏出情况对照 |
